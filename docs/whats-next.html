03接下来四件事

按顺序做，不要并行。每件事都能独立收尾、独立验收。

下一步 · 1 个晚上

A. 把 WAL 接进 DB

这是唯一一件「组件已经写完、只是没接线」的事。收益最大、风险最小、见效最快。 做完之后，你的系统才第一次满足存储引擎的及格线：进程被 kill -9，数据还在。 现在不满足 —— 现在靠 ~LSMDB() 里强行刷盘，那是走运，不是设计。

  1. LSMDB 加一个 std::unique_ptr<AppendOnlyLog> wal_
  2. DB::Open 时打开 wal.log，把里面的记录重放进 MemTable
  3. Put / Delete 改成：先 wal_->Append(record)，再写内存
  4. 刷盘成功之后，清空 WAL
  5. 删掉 ~LSMDB() 里那段强行刷盘
第 4 步是唯一需要想清楚的地方：什么时候可以安全地扔掉日志？ 答案只有一句 —— 当这批数据已经落到别的地方了。想不清就会写成 「日志清早了 = 丢数据」或者「从不清 = 磁盘被日志撑爆」。这两个错误都真实存在。

验收：写一半 kill 掉进程，重启后数据还在；再跑一次正常的 demo_restart，结果不变。

完成之后你能回答什么

「一次 Put 请求按什么顺序落盘，为什么不能反过来？」

「WAL 会不会无限增长？什么时候能清？」

「fsync 的代价有多大，能不能等到一批再 fsync？」（后者叫 group commit，LevelDB 就有）

考研后 · 2–3 个晚上

B. compaction

现在 .sst 只增不减：每刷一次盘多一个文件，Get 要挨个扫， 删掉的 key 占的空间永远不回收。跑久了会变成「20 个文件扫 20 次」。

  1. 挑相邻的两三个文件
  2. 归并读出来：同一个 key 谁新谁赢，用归并而不是全量排序
  3. 写成新的 .sst，删掉旧文件
唯一的陷阱：墓碑不能随便丢。只有当「更老的层里确定没有这个 key」时， 墓碑才可以被扔掉。丢早了，下面那层的旧值立刻复活 —— 你已经踩过一次这个坑了， 这次它会以「跨文件」的形式再来一次。

验收：合并前后所有 key 的 Get 结果逐条一致；文件数从 N 降到 1 到 2 个。

完成之后你能回答什么

「读放大、写放大、空间放大分别是什么，compaction 在换什么？」

「 leveled 和 tiered 有什么区别？RocksDB 为什么两个都留着？」

考研后 · 2–3 个晚上

C. 后台刷盘线程

现在 FlushImmutable() 是在 Put 里同步调的： 写满一张表的那一刻，这个写请求要等文件写完才返回。 真实引擎不让写等刷盘 —— 这正是当初设计 immutable 的原因，现在还没兑现。

  1. 一个后台线程 + 一个待刷队列（或直接用 immutable_ 当队列）
  2. 主线程 Rotate 完就返回，后台线程接手刷
  3. 刷不过来时怎么办：堵住写（write stall）还是继续收（内存涨）—— 二选一，说清理由

验收：刷盘期间持续 Put，观察单次 Put 的延迟没有出现尖刺。

完成之后你能回答什么

「为什么是 unique_ptr 而不是 shared_ptr？」（这道题你已经答过一遍了）

考研后 · 1 个晚上

D. 一组能信的性能数字

现在 demo_sstable 的第 [6] 项跑出来是「40000 条比 5000 条快 4 倍」。 断言通过了，但这个数字什么都没证明 —— 先跑的那组是冷的，后跑的在 CPU 缓存里。 测试通过 ≠ 测对了。

  1. 每组先跑一轮热身，丢弃结果
  2. 两组交替跑 5 次，取中位数而不是单次
  3. 固定数据集和随机种子，报告 P50 / P99 而不只是均值

验收：连跑三遍，数字波动在 ±10% 以内。

完成之后你能回答什么

「你怎么证明它快？」—— 有数字、有方法、知道自己的数字哪里不可信，比数字好看更有说服力。

04面试怎么讲

项目做完不等于能讲。这一段现在就可以背下来。

三十秒版（简历上写的就是这段）

用 C++17 从零实现了一个 LSM-Tree 存储引擎：WAL 保证崩溃不丢数据， 跳表做内存表，SSTable 带稀疏索引和二分查找，写入按 WAL → 内存表 → 冻结 → 落盘的路径走， 把随机写转换成顺序写。附带 17 个可执行验收程序，覆盖崩溃恢复、墓碑语义和随机对拍。

三分钟版（讲两条路径 + 一个 bug）

写：先 append 到 WAL 并 fsync，再写跳表；写满就冻结成 immutable，换一张新表继续收写入， 后台把冻结表刷成 SSTable，刷完才敢清 WAL。

读：先查 active，再查 immutable，都是三态结果（有值 / 墓碑 / 没有）； 只要命中值或墓碑就停手，只有「没有」才往下查磁盘，磁盘从新到旧，墓碑同样终结。

踩过的坑：一开始我把内存查找的返回值收成 Status，只有成功和失败两态， 结果「内存里有墓碑」和「内存里没有」变成了同一个值，去查磁盘时把删掉的数据读了回来。 这个 bug 不崩、不报错，只是删了又活 —— 后来才明白返回值的信息量必须够调用方做判断。
