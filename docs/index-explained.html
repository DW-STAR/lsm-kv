索引到底在干什么

SSTable v2 · 从 1048 个真实字节讲起 · 2026-11-18

一句话：索引就是书的目录。你查一条 key，不用从第 1 页翻到第 960 页，先翻目录找到大概在哪儿，跳过去，翻两页就找到了。

你晕是正常的。前面 v1 只干了一件事 —— 证明「写出去能原样读回来」，那时候整个文件里只有数据。现在突然多出一段你不认识的东西，还改了 footer 长度，看起来像凭空长出来的。

其实不是凭空。下面按「为什么要加 → 加在哪 → 长什么样 → 怎么用」四步走。

00为什么会「突然」多出一段

因为 v1 的验收线过了。这两个阶段的目标是分开的，而且不能同时抓：

阶段唯一目标可以不管的
v1字节格式正确 —— 写出去、读回来、每个字节对得上性能（全扫也行）
v2查询不要读全表字节格式（记录的 24 字节一个都没改）
为什么不能一起做？ 如果一上来就写「格式 + 索引」，出了 bug 你分不清是记录编码错了还是索引定位错了 —— 两个都是「查不到这条 key」，症状一模一样。分开做，v1 全绿就是一条干净的基线，后面所有异常都能归因到索引。

所以「突然多出一段」的真相是：数据区的格式已经被冻结了，我们只是在文件末尾追加了两块东西。记录还是 [CRC 4B][type 1B][klen 4B][key][vlen 4B][value]，一个字节都没动。

01先看 v1 有多慢

这是你自己跑出来的 demo_sstable 第 [6] 段的数字：

数据量200 次查询总耗时单次
5 000 条328 ms1.64 ms
40 000 条2 468 ms12.3 ms

数据量 ×8，耗时 ×7.8。正比。这就是 O(N) 的样子 —— 多一条记录，查询就多扫一条。

而这个数字还是「整个文件已经在内存的 std::string 里」的时候测的。真实引擎里每一次扫都要从磁盘读，代价还要再乘上几个数量级。

算一笔账：100 万条记录、平均每次查 50 万条 —— 就算每条只要 20 纳秒（纯内存比较，非常乐观），一次查询也要 10 毫秒。一个数据库每秒只能回答 100 个查询。这不是「慢一点」，这是不可用。

02索引 = 目录。就这么简单

想象一本 960 页的书，40 章，每章 24 页。你要找第 38 章：

  • 没有目录：从第 1 页一页页翻 → 翻 888 页
  • 有目录：看目录写着「第 33 章 · 第 769 页」→ 直接跳到 769 页，往下翻 5 页

关键在目录只写了 3 行，不是 40 行：

第 1  章 ......... 第 1   页
第 17 章 ......... 第 385 页
第 33 章 ......... 第 769 页

每 16 章记一行。为什么不满满当当写 40 行？因为 目录写满了就等于把书抄了一遍 —— 那还不如直接翻书。

映射到 SSTable，一模一样：

书SSTable
第 33 章一条记录（比如 k032）
第 769 页这条记录在文件里的偏移（比如 768）
每 16 章记一行每 16 条记录记一个锚点（kIndexInterval = 16）
目录索引区（index_，落盘后是文件里的一段）

「稀疏索引」这个词说的就是这件事：不是每条都记，是隔一段记一个。省下来的空间，换来的是「多扫几页」。

03真实文件长什么样

我写了个工具，用 SSTableBuilder 生成了 40 条记录（k000…k039，value 是 val-000…val-039），然后把它拆开。整个文件 1048 字节，分三段：

0
数据区 data960 字节 · 40 条记录
每条 24 字节，按 key 升序紧挨着排。v1 就这么多，一个字节没变。
960
索引区 index48 字节 · 3 项 × 16 字节
v2 新增。每项 = 一个 key + 它在数据区的位置。
1008
footer40 字节 · 5 个 uint64
v1 是 24 字节 3 个字段，v2 变成 40 字节 5 个字段。

文件总长 1048 = 960 + 48 + 40

这个 1048 是不是刚好能对上？因为我们特意挑了整齐的数据：

一条记录 = 4(CRC) + 1(type) + 4(klen) + 4("k000") + 4(vlen) + 7("val-000")
         = 24 字节

40 条记录        = 24 × 40      = 960       ← data_end
一块 16 条       = 24 × 16      = 384       ← 锚点间距也是 384
40 条 → 3 块     = 16 + 16 + 8  = 40 条
3 个锚点 × 16 B  = 48 字节                  ← 索引区
footer           = 40 字节
                                     合计 = 1048
注意最后一块只有 8 条。40 不是 16 的整数倍，所以第三块「不满」。索引里不会有第 4 个锚点 —— 因为锚点只在「第 0、16、32 条」这三个位置记。这是稀疏索引的自然结果，不用特殊处理。

04索引项：16 个字节，就两样东西

索引区里 3 项，原始字节是这样（从文件里逐字节读出来的，不是我编的）：

[960]  04 00 00 00  6B 30 30 30  00 00 00 00 00 00 00 00
[976]  04 00 00 00  6B 30 31 36  80 01 00 00 00 00 00 00
[992]  04 00 00 00  6B 30 33 32  00 03 00 00 00 00 00 00
klen · 4 字节 key · 变长 offset · 8 字节

拆开读：

klenkeyoffset什么意思
04k0000第 0 条记录在文件第 0 字节
04k016384第 16 条记录在文件第 384 字节
04k032768第 32 条记录在文件第 768 字节

80 01 00 00 00 00 00 00 就是 384 —— 小端，低字节在前。0x180 = 384。00 03 00… 是 0x300 = 768。这些数你手算也能对上（16 × 24 = 384，32 × 24 = 768），这就是为什么我挑了这么整齐的数据。

为什么 key 前面要记一个 klen

因为 key 是变长的。k000 是 4 字节，但真实项目里 user:10086:profile 是 18 字节。没有长度，你读到哪儿算一个 key 结束？只能靠猜。

这和 record.h 里一条记录的结构是同一个套路 —— 变长字段前面必须有一个长度。这个模式你会在这行代码里见到一百次。

为什么 offset 要 8 字节

4 字节最大 4GB。单个 SSTable 一般到不了 4GB，但「刚好够用」的字段类型是存储系统里最常见的静默 bug 来源：超过的那天它不会报错，它会绕回去。长度和偏移这类字段，宁可宽一档。

05footer：从 3 个字段变 5 个

v1 的 footer 是 [data_end][count][magic] = 24 字节。v2 要能定位索引区，所以多了两个：

位置字段值作用
+0data_end960数据区到哪儿结束
+8index_offset960索引区从哪儿开始
+16index_count3索引有几项
+24record_count40数据区有几条记录
+32magicLSMSST02印章 + 版本号

真实字节：

C0 03 00 00 00 00 00 00   → 960    data_end
C0 03 00 00 00 00 00 00   → 960    index_offset
03 00 00 00 00 00 00 00   → 3      index_count
28 00 00 00 00 00 00 00   → 40     record_count
32 30 54 53 53 4D 53 4C   → "LSMSST02"（小端倒着看）

为什么 data_end 和 index_offset 现在相等，还要各记一份

此刻它们必然相等 —— 数据区写完之后，索引紧接着开始，中间什么都没有。那为什么记两份？

  • 交叉验证：如果哪天它们不相等而格式规定必须相等，就是文件被改过或有空洞，可以报 Corruption。
  • 给中间留位置：后面要插布隆过滤器、统计信息（最小 key、最大 key、压缩算法标识…），那时候两者就分开了。现在就把字段留好，那天不用再改一次格式。
magic 也换了。v1 是 LSMSST01，v2 是 LSMSST02。同一个「LSMS」前缀 + 不同版本号。这样读到 v1 老文件时能精确说「版本不对」，而不是笼统的「magic 不对」—— 前者要做兼容或重建，后者说明你打开的根本不是这个文件。两种错误要干的事完全不同。

06查一条记录，到底怎么走

现在拿 k037 来试。它在第三块里（k032…k039）。

整个过程两步：先在索引里二分，找到「我可能在哪个块」，再进那个块顺着扫。

k000offset 0
k016offset 384
k032offset 768
目标 key = k037　·　索引里有 3 个锚点，二分最多 2 步
点下面按钮开始。

最后一步是关键：块内从 offset 768 开始，用 Decode 一条条往下解，最多扫 16 条。实际扫了 6 条（k032 → k037）就命中了。

v1 怎么查

38 条
从 offset 0 一路 Decode 到 k037，每条都比一遍

v2 怎么查

2 + 6
2 次索引比较，定位到块；块内扫 6 条

40 条数据看不出多大差别（38 vs 8）。但差距是跟着数据量线性放大的 —— 见下一节。

07二分到底在比什么（这里最容易写错）

你要找的不是「第一个 ≥ target 的锚点」，而是「最后一个 ≤ target 的锚点」。

为什么？因为索引项的含义是「这一块的起点」。如果你找 k037：

  • 第一个 ≥ k037 的锚点 = k032？不对，k032 < k037，所以没有 ≥ 它的锚点。按这个找法你会落到「头」或者「尾」，全错。
  • 最后一个 ≤ k037 的锚点 = k032 ✅ 因为 k037 一定落在「k032 开始的那一块」里（k032 到 k039 之间）。

换个角度想：锚点 k032 说的是「从这个位置开始，之后的 key 都 ≥ k032」。既然 k037 ≥ k032，那 k037 只可能在 k032 之后。而锚点 k048（如果有）说的「之后都 ≥ k048」对 k037 不成立，所以 k037 一定在它之前。

所以：找最后一个 key ≤ target 的锚点，那块就是它的候选块。

uint64_t lo = 0, hi = index_.size();
while (lo < hi) {
  const uint64_t mid = lo + (hi - lo) / 2;
  if (index_[mid].key <= target) lo = mid + 1;   // mid 这块可能含 target，往右
  else                          hi = mid;        // mid 太大，往左
}
// lo 是「第一个 > target 的锚点」，所以候选块是 lo - 1
const uint64_t block = (lo == 0) ? 0 : lo - 1;
边界陷阱：lo == 0 的情况必须单独处理。它意味着所有锚点都 > target（target 比最小的 key 还小），这时应该从第 0 块开始扫 —— 而不是「lo - 1」变成 0 - 1 这个巨大的无符号数，然后越界读。

和 Seek 里那个 p 停在左邻、返回 p->next[0] 是同一类问题：指针/下标停在「左边那一格」时，要单独想清楚「左边没有格子」怎么办。

顺便，代码里 lo + (hi - lo) / 2 而不写 (lo + hi) / 2：后者在 lo 和 hi 都很大时会整数溢出。索引项数量到不了这个规模，但这是二分查找的标准写法，照着写不会有坏处。

08为什么是 16，不是 4，也不是 64

这是一个纯粹的权衡，没有正确答案，只有「在什么场景下更合适」。

间隔调小（比如 4）

好：块内只扫 4 条，快
坏：索引变成数据的 1/4，空间暴涨

间隔调大（比如 64）

好：索引只占 1/64，省空间
坏：块内最多扫 64 条，慢

总代价大致是：log₂(N/16) 次索引比较 + 16 次块内扫描。间隔变大，第一项变小（但 log 变化极慢），第二项线性变大。所以间隔主要影响第二项 —— 它应该跟「一次 I/O 读进来多少字节」对齐，而不是跟「记录条数」对齐。

LevelDB 的做法更彻底：它不按「每 N 条」切块，而是按「每 4KB」切 —— 因为磁盘一次读的最小单位就是 4KB 左右的页。读一块 = 一次 I/O。我们按条数切是为了好讲，等做 compaction 的时候可以改成按字节。

09复杂度账：100 万条的时候差多少

同样查一条 key，两种做法的步数：

数据量v1 全扫v2 索引倍数
40 条382 + 6 = 84.8×
1 万条~5 00010 + 16 = 26190×
100 万条~500 00016 + 16 = 3215 000×

100 万条那一行怎么来的：

索引项数 = 1 000 000 / 16 = 62 500
二分步数 = log₂(62 500) ≈ 16
块内扫描 = 最多 16 条
合计     ≈ 32 步

v1 平均要扫一半 = 500 000 步
倍数     = 500 000 / 32 ≈ 15 600

这就是「O(N) 变 O(log N)」的实际意义。不是「快一点」，是「数据量涨 25 倍，查询步数只多 1 步」。

10还没做的东西（别以为索引做完了就完了）

  • Open 还是把整个文件读进内存。索引再快，文件本身 2MB 全灌进 data_ 也白搭。真实引擎是 pread 只读需要的那几 KB。
  • 数据区没有块级校验。现在每条记录有自己的 CRC，但如果某个长度字段被改坏，你连「下一条从哪儿开始」都不知道。LevelDB 的解法是每 4KB 块自带一个 CRC —— 就算块内全乱了，块边界仍然可信。
  • 索引区本身没有校验。它也是磁盘上的字节，也会坏。
  • 没有布隆过滤器。查一个根本不存在的 key，现在仍要走完全程（二分 + 扫一块）。布隆过滤器能在读磁盘之前就说「这个 key 肯定不在」，省掉整趟 I/O。

这些都不急。今天的验收线是：索引能正确写出去、正确读回来、查询结果和全扫完全一致。
