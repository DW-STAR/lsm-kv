# 这个项目用到的 C++ 特性

> **这是手册，不是课文。** 不用从头读到尾。
> 看到代码里有个不认识的东西，来这里查，只查那一条。

查的时候只看一个问题：**「没有它，会出什么事？」**
C++ 的每个特性都是为了堵一个具体的坑。记住坑，特性自然就记住了。

## 1. `#pragma once`

**没有它会出什么事**：`a.h` 和 `b.h` 都包含了 `slice.h`，你的 `main.cpp` 又同时包含 `a.h` 和 `b.h`。于是 `slice.h` 的内容被**贴了两遍**进 `main.cpp`，`class Slice` 被定义了两次 → 编译报错 `redefinition of 'Slice'`。

`#pragma once` 的意思就是：**这个文件在一次编译里只准贴一遍。**

> 严格说这是编译器扩展，不是 C++ 标准。但 GCC / Clang / MSVC 全支持，LevelDB 也这么写，放心用。
> 标准写法叫「头文件保护」（`#ifndef SLICE_H ... #endif`），效果一样但更啰嗦。

---

## 2. `#include <...>` vs `#include "..."`

| 写法 | 去哪找 |
|---|---|
| `#include <vector>` | 编译器的**系统库**目录 |
| `#include "slice.h"` | **先**找当前文件所在目录，找不到再去系统目录 |

所以标准库用尖括号，自己写的用引号。

**`#include` 就是「复制粘贴」**，没有任何魔法。编译到这一行，预处理器把那个文件的全文原样倒进来。
想亲眼看到？`g++ -E main.cpp -o main.i`，打开 `main.i`，你会发现几万行 —— 那就是贴完的样子。

## 3. `namespace lsmkv`

**没有它会出什么事**：你写了个 `class Status`，引了某个第三方库，人家也有个 `class Status`。链接的时候两个 `Status` 撞在一起 → 报错，而且报错信息完全看不懂（会说「重复定义」，但你翻遍自己的代码找不到第二个）。

`namespace` 就是给名字加个门牌号：

```cpp
namespace lsmkv {
class Status { /* ... */ };
}

lsmkv::Status s;   // 明确指向我这个
other::Status s2;  // 人家的，井水不犯河水
```

**注意末尾那个 `}  // namespace lsmkv` 的注释** —— 不是废话。文件长了以后，你看到一坨 `}` 根本不知道在关哪个，这个注释是给人看的。

## 4. `class` + `public:` / `private:`

**没有它会出什么事**：`entries_` 这个 vector 谁都能直接 `log.entries_.clear()`。别人（或者三个月后的你）一句话就把日志清空了，而 `size()` 还以为里面有一堆数据。整个类的正确性靠「大家都守规矩」来保证 —— 这在工程上等于没有保证。

```cpp
class AppendOnlyLog {
 public:                      // 外面能调的
  void Append(...);
  bool Get(...);
  size_t size() const;
 private:                     // 只有自己能用
  std::vector<...> entries_;
};
```

`private` 的意思是：**这个变量长什么样，是我这个类自己的事。** 外面只能通过 `Append` / `Get` 跟我打交道。哪天我把 `vector` 换成 `list` 或者换成文件，外面的代码一行都不用改。

这叫**封装**。面试问「什么是封装」，标准答案就是这个 —— 不是背的，是你的代码里天天在干的事。

> 补充一个反直觉的点：`public` / `private` 是**编译期**概念，运行时零开销。检查完就没了，不会让程序变慢。

## 5. 成员函数后面的 `const`

```cpp
bool Get(const std::string& key, std::string* value) const;
//                                                 ^^^^^ 这个
```

**没有它会出什么事**：你有一个 `const AppendOnlyLog& log`（比如某个函数参数写成了 const 引用，表示「我保证不改你」），然后你想调 `log.Get(...)`。如果 `Get` 没标 `const`，编译器会拒绝：**「你说不改，但你要调的这个函数我可不能保证它不改。」**

标了 `const` 就是签了个合同：**这个函数体内不许修改成员变量。** 编译器会强制检查 —— 你在 `Get` 里写一句 `entries_.clear()`，立刻报错。

合同签了，换来的是：任何 `const` 对象都能调它。

> 判断标准很简单：**这个函数改不改我的数据？不改就标 `const`。**
> 你的 `Append` 改了 → 不标。`Get` 只读 → 标。`size` 只读 → 标。

## 6. `&` 引用 vs `*` 指针

```cpp
void Append(const std::string& key, const std::string& value);   // 引用
bool Get(const std::string& key, std::string* value);            // 指针
```

**为什么两个参数一个是引用一个是指针？** 因为职责不同：

| | `&` 引用 | `*` 指针 |
|---|---|---|
| 本质 | 别名，就是那个变量本身 | 一个存地址的数 |
| 能不能为空 | **不能**，必须绑到东西上 | 能，可以是 `nullptr` |
| 能不能改绑 | 不能，绑上就一辈子 | 能，随时指向别的 |
| 用之前要不要检查 | 不用 | 要（不查就崩） |

第一条 `key`：**必须给我一个 key，没有「没有 key」这种情况** → 用引用，天然保证非空。
第二条 `value`：**输出参数**，我要往里写东西。用指针是为了在调用处一眼看出来「这个会被改」：

```cpp
std::string v;
log.Get("name", &v);   // 看到 & 就知道 v 要变
```

> 输出参数用指针、输入参数用 const 引用 —— 这是 C++ 的老习惯（Google 代码规范就这么写）。你在别人的代码里会一直看到。

**关键的一点：`const std::string&` 是「零拷贝」。**
如果写成 `std::string key`（传值），每次调用都要把整个字符串复制一份。key 短无所谓，value 要是 1MB 呢？每次 Put 都复制 1MB，白给。
加上 `&` 就不复制了 —— 直接操作原来那个。加上 `const` 就是「我只看，不碰」。

> **三个词连起来读：`const std::string&` = 「借我看一下，我不改，也不复制」。** 工程代码里出现频率最高的一个组合。

## 7. `static constexpr`

```cpp
static constexpr const char* kTombstone = "__DELETED__";
```

拆成三段看：

| 部分 | 作用 |
|---|---|
| `static` | 这个常量属于**整个类**，不属于某个对象。100 个 `AppendOnlyLog` 也只有一份 `kTombstone`，不占每个对象的内存 |
| `constexpr` | 编译期就确定值。编译器直接把它当字面量用，运行时连读内存都省了 |
| `const char*` | 类型：指向只读字符的指针 |

**没有 `static` 会怎样**：每个 `AppendOnlyLog` 对象里都存一份指针（8 字节），浪费，而且逻辑上它本来就不是「每个日志各自的墓碑」。

> **命名约定**：`kTombstone` 开头那个 `k` 是 Google 代码规范里「常量」的前缀（k = constant）。LevelDB 满篇都是 `kBlockSize`、`kMaxSequenceNumber`。看到 `k` 开头就知道是常量。

## 8. `std::string` vs `const char*`

```cpp
void Append(const std::string& key, const std::string& value);
// ...
Append(key, kTombstone);   // kTombstone 是 const char*，怎么就传进去了？
```

因为 `const char*` → `std::string` 有**隐式转换**：编译器会临时造一个 `std::string` 对象，把 `"__DELETED__"` 拷进去，然后把这个临时对象绑到引用上。

两者根本不是一回事：

| | `const char*` | `std::string` |
|---|---|---|
| 本质 | 一个地址，后面跟着一串字符，靠 `\0` 结尾 | 一个对象，**自己管着一块内存** |
| 知道自己的长度吗 | 不知道（要 `strlen` 从头数） | 知道，`.size()` O(1) |
| 能不能存 `\0` | 不能，会被当结尾 | 能 |
| 谁负责释放内存 | 手写 `free`，忘了就泄漏 | 析构函数自动释放（RAII） |

**这就是为什么我们的接口用 `std::string`**：它在析构时自动释放内存，你不可能忘。C 风格字符串必须手动管，是所有内存泄漏事故的源头。

> 顺便解释了你之前那个问题：「为什么 `Delete` 里写 `Append(key, kTombstone)` 能过编译」—— 不是类型匹配，是编译器悄悄帮你造了个临时 `std::string`。
> **代价**：每次 Delete 都多一次字符串拷贝 + 一次内存分配。极小，但这个「能省则省」的思路正是 `slice.h` 存在的理由 —— `Slice` 不拥有内存，只借看，连拷贝都免了。

## 9. `std::vector` + `emplace_back`

```cpp
std::vector<std::pair<std::string, std::string>> entries_;
entries_.emplace_back(key, value);
```

`vector` = **一段连续的内存**，能自动扩容（满了就申请一块更大的，把旧的搬过去，通常是 2 倍）。连续意味着：按下标访问 O(1)，而且对 CPU 缓存极其友好 —— 这是它比链表快得多的真实原因（不是「链表插入快」这种教科书话术）。

`emplace_back(key, value)` vs `push_back({key, value})`：

- `push_back` 要**先造一个** `pair` 临时对象，再把它**移动**进 vector。
- `emplace_back` 直接把参数**原地**传给元素的构造函数，在 vector 的内存里直接造出来。少一次构造。

对一个 `pair<string,string>` 来说差别很小，但这是习惯问题 —— 能原地造就别先造再搬。

> 顺带说，**为什么这里用 vector 不用 map？**
> 因为「只追加」要求保留**每一条历史记录**。`map` 的语义是「一个 key 只有一个 value」，你一 `map[key] = v`，旧的就没了 —— 恰好把我们要的东西删掉了。
> 这个设计如果换成 `map`，整个 LSM 的思想就塌了。

## 10. `std::pair` + `.first` / `.second`

`std::pair<A, B>` 就是把两个值捆成一个整体。字段名固定叫 `.first` 和 `.second`（难听，但标准就这样）。

所以 `Get` 里这两行：

```cpp
if (it->first != key)  continue;      // first 是 key
if (it->second == kTombstone) ...     // second 是 value
```

`it` 是个迭代器，`it->first` 等价于 `(*it).first`。

> 用 `pair` 是因为它够用。等到要加「时间戳」「记录类型」这些字段时，`pair` 就不够了，得自己定义结构体：
> ```cpp
> struct Record { std::string key; std::string value; bool deleted; };
> ```
> **记住这个变化** —— 它就是「落盘」那一步马上要做的事。

## 11. `auto`

```cpp
for (auto it = entries_.rbegin(); it != entries_.rend(); ++it)
```

`auto` = 让编译器根据右边推导类型。这里 `it` 的真实类型是：

```cpp
std::vector<std::pair<std::string, std::string>>::const_reverse_iterator
```

手写这一长串纯粹是自虐，还容易打错。`auto` 就是为这种场景发明的。

**限制**：`auto x;` 不合法 —— 没有初始值就无从推导。
**注意**：`auto` 会**丢掉** `const` 和引用（`auto x = v;` 是拷贝一份）。要保留得写 `auto& x = v;` 或 `const auto& x = v;`。

---

## 12. `rbegin()` / `rend()`

普通迭代器从头往尾走：`begin()` → `end()`。
`r` = reverse：`rbegin()` 指向**最后一个**元素，`rend()` 在第一个元素**之前**。

关键点：**倒着走也是用 `++it`**。逆序迭代器的 `++` 已经被重载成「往前走一个」了。

```cpp
for (auto it = entries_.rbegin(); it != entries_.rend(); ++it)
```

这就是「后写的赢」的全部实现：**从最新的那条往回翻，翻到的第一条就是答案。** 不用比较时间戳，不用排序，位置本身就编码了时间。

---

## 13. `size_t`

`size_t` 是专门表示「大小 / 下标」的**无符号整数**类型（通常 64 位）。`sizeof` 返回它，`vector::size()` 返回它。

为什么不用 `int`？因为 `int` 有负数，而「长度是 -1」没有意义；而且 32 位 `int` 装不下大于 2GB 的容器大小。

> 需要 `#include <cstddef>` 才能用它。这就是 `append_only_log.h` 第一行那个 include 的用处 —— 它没有一行是白写的。

## 14. 头文件到底装什么

这个问题不搞清楚，你迟早会遇到 `undefined reference` 和 `multiple definition` 两种报错，而且分不清。

先记住一件事：**编译器一次只处理一个 `.cpp` 文件**（叫一个「编译单元」）。它完全不知道别的 `.cpp` 里有什么。

于是分工是：

| 放在 `.h` 里 | 放在 `.cpp` 里 |
|---|---|
| **声明**：这东西存在，长这样 | **定义**：这东西的实现 |
| `class` 的成员列表 | 成员函数的具体代码（**除了**类内直接写的那种） |
| 函数原型 `void f(int);` | `void f(int x) { ... }` |
| 模板、`inline` 函数、`constexpr`（**必须**放头文件） | 普通函数的实现 |

**为什么模板必须放头文件？** 因为编译器要看到模板的完整代码才能生成具体版本。只给声明，它生成不出来，链接时就找不到 → `undefined reference`。

> 我们的 `AppendOnlyLog` 所有函数都**直接写在类体里**。这不是偷懒 —— C++ 规定「定义在类体内的成员函数自动是 `inline`」，所以写进头文件不会违反「一个定义只能有一次」的规则。
> 这是写小类的常见做法。类一大（像 LevelDB 的 `DBImpl`，几千行），就必须拆成 `.h` 声明 + `.cpp` 实现，否则每个包含它的文件都要重新编译几千行。

## 15. 为什么不用 `bits/stdc++.h` + `using namespace std`

你的 ACM 码风：

```cpp
#include <bits/stdc++.h>
using namespace std;
```

**在竞赛里这是对的** —— 只写 200 行，只为 3 小时内出结果，编译慢一秒无所谓，跟别人的代码永不共存。

**在工程里这是错的**，三个理由，按重要性排：

**① 冲突。** `using namespace std` 把 `std` 里**所有**名字倒进全局空间。你定义一个 `count`、`distance`、`data`、`left`、`right`、`size`，随时可能跟 `std::count`、`std::distance`、`std::size` 撞车。这类 bug 报错信息极其莫名其妙。

**② 编译时间。** `bits/stdc++.h` 是「把整个标准库全包含进来」，一个空程序编译要 1 秒以上。大项目几百个文件，这个开销乘以几百。我们只 include 真正用的（`<string>`、`<vector>`、`<cstddef>`）。

**③ 可读性 / 面试印象。** `std::string` 一眼看出这是标准库的，`string` 得靠上下文猜。**大厂 C++ 岗的代码 review 风格就是这样 —— 前缀写全。** 面试官看到一段满屏 `using namespace std` 的工程代码，会怀疑你只写过算法题。

> **这是码风差异，不是对错。** 刷题时你想怎么写就怎么写，那是你的主场。进了这个项目就按工程规范来 —— 你正在练的恰好就是「从算法选手变成工程选手」这件事。

### 关于缩进 2 格

`2` 空格 = Google C++ 风格 = **LevelDB 的代码**。你以后翻 LevelDB 源码，会发现跟这个项目长得一模一样 —— 这是故意的，为了你读源码时不别扭。

想改成 4 格（你顺手的那种），打开 `D:\code\lsm-kv\.clang-format`，把里面两个 `2` 改成 `4` 就行。**改不改都行，统一就行。**

## 16. 用 `std::string` 装字节

**没有它会出什么事**：什么叫"没有它"——这里的问题是"为什么教材不这么教，而项目这么干"。

先说清楚三件事：

**① 教材里 `std::string` 只装文本。** 所以你在课本、在刷题、在任何例题里都没见过它装二进制。**你没见过是正常的，不是漏学了什么。**

**② 正经类型是 `std::vector<char>`。** 它语义正确：一个 char 数组，不代表文本，就是一堆字节。

**③ 项目里用 `std::string`，是工程习惯。** 两个理由：

```cpp
std::string out;
out.append(key);                       // 追加方便
f.write(out.data(), out.size());       // 能直接喂给 write()
```

`vector` 也能干这两件事，但 string 的 `append` 更顺手，而且 `data()` 保证连续。**LevelDB 源码里就是 `std::string`。** 所以这是行业惯例，不是错误。

### ⚠️ 唯一的坑（很重要）

```cpp
std::string s;
s.push_back('\0');        // 合法！string 里可以装 0
s.append("abc");
s.size();                 // 4  ← 正确
strlen(s.c_str());        // 0  ← 错！遇到 '\0' 就停了
printf("%s", s.c_str());  // 什么也不打印
```

**string 里可以合法装 `\0`，所以它有两个"长度"概念：`size()` 是真长度，`c_str()` 是给 C 函数看的、遇 `\0` 截断。**

装字节的时候：**永远用 `size()`，永远别把它当 C 字符串用。** 这一条违反了就是数据丢失的 bug，而且极难查——因为"存进去了但读不出来"。

> 判断标准：**你要的是"一段字节"还是"一句话"？**
> 是字节 → 用 `size()`，别碰 `strlen` / `printf("%s")` / `strcmp`。
> 是文本 → 随便用。

## 17. 十六进制怎么看

**没有它会出什么事**：看到 `6e 61 6d 65` 完全读不出意思，只能干瞪眼。

一句话：**1 个字节 = 2 个十六进制位，一一对应，不多不少。**

| 十进制 | 十六进制 | 二进制 |
|---|---|---|
| 0 | `0` | 0000 |
| 9 | `9` | 1001 |
| 10 | `a` | 1010 |
| 15 | `f` | 1111 |
| 110 | `6e` | 0110 1110 |
| 255 | `ff` | 1111 1111 |

**为什么不用二进制？** 一个字节要写 8 个 0/1，`6e` 写成 `01101110`——满屏的 0 和 1，眼睛会瞎。十六进制刚好 1 个字符管 4 位，2 个字符管 1 字节，**是"人眼能看的最小单位"**。

**为什么不用十进制？** 因为 255 的十进制是三位数，一个字节要占 3 个字符，而且跟二进制没有整齐对应。十六进制能一眼看出位模式。

### 怎么读一段十六进制

以 `01 04 00 00 00 6e 61 6d 65` 为例：

1. **先按你定的格式分段**（1 / 4 / klen / 4 / vlen），别当一个整体看。格式是你的，只有你知道边界在哪。
2. **小端序**：`04 00 00 00` 要**倒着读**成 `00 00 00 04` = 4。低位字节在前。
3. **ASCII 段直接翻译**：`6e 61 6d 65` → `n a m e`。常用就那几个：`0x20` 空格、`0x30~0x39` 是 `0~9`、`0x41~0x5a` 是 `A~Z`、`0x61~0x7a` 是 `a~z`。

> **实用技巧**：怀疑某段是不是文本，就把那段的十六进制丢给在线工具或记事本——能转出人话就是文本，转出乱码就是二进制。
> **更实用的技巧**：别手算。写个 `PrintHex()`（`demo_record.cpp` 里已经有了），跑一次看一眼，比对着看十分钟强。

> 十六进制本身**没有任何计算含义**，它只是"把字节显示给人看"的眼镜。你觉得别扭，只是没戴过这副眼镜——戴上几次就自动会了，不需要"学"。

## 18. `uint32_t` 为什么不直接用 `int`

**先给个不痛快的回答**：在你这台机器上，把 `uint32_t` 全换成 `int`，今天照样跑得通。`sizeof(int)` 在 Windows x64 上就是 4。

**但那是碰巧。**

### 先拆名字

```
uint32_t
 u    int   32   _t
 │     │    │    └─ "type" 的约定后缀，表示"这是个类型"
 │     │    └─ 32 位
 │     └─ integer，整数
 └─ unsigned，无符号（没有负数）
```

读作：**无符号、32 位的整数类型**。需要 `#include <cstdint>`。

### 关键区别：宽度是否固定

| 类型 | 宽度 | 能表示的范围 |
|---|---|---|
| `int` | **不保证**。标准只说「至少 16 位」，实际看编译器/平台 | 视宽度而定 |
| `unsigned int` | 同上，不保证 | 无负数 |
| `uint32_t` | **保证正好 32 位** | 0 ~ 4,294,967,295 |
| `size_t` | 保证跟指针一样大：32 位平台 4 字节，64 位平台 8 字节 | 无负数 |

> `int` 不保证 32 位不是理论问题：16 位 DOS、部分嵌入式编译器里 `int` 就是 16 位。你现在用的 MSVC / MinGW 是 32 位，**换个编译器可能就不是**。

### 为什么落盘必须钉死宽度

**因为文件要跨越编译器、平台、和时间。**

你今天用 `int` 写了 4 字节进文件，明天换台机器（或换个编译器版本），如果那边 `int` 是 2 字节，读的时候只读 2 字节 → **后面所有字段全部错位**，读出满屏乱码。

而 `uint32_t` 不管在哪台机器上都是 4 字节。**这就是「可移植性」的全部含义**：不是跑得快，是换个环境也不出错。

### 为什么必须"无符号"

这一条在你的 `Decode` 里是真会炸的：

```cpp
const uint32_t klen = GetFixed32(&p, limit);
if (p + klen > limit) return false;      // 文件坏了 → 这里挡住
```

假设文件被改坏，那 4 个字节是 `FF FF FF FF`：

| 类型 | 读出来的值 | `p + klen` 之后 | 结果 |
|---|---|---|---|
| `int`（有符号） | **-1** | `p - 1`，游标**往回走** | 检查通过 ✗ → `assign(p, -1)` → 转成 `size_t` 变成天文数字 → 崩 |
| `uint32_t`（无符号） | **4294967295** | 一个巨大的地址 | `> limit` 成立 → `return false` ✓ |

**有符号会把「文件坏了」变成一个负偏移，绕过你的边界检查。** 长度、大小、下标这类东西，永远用无符号。

### `const` 是干嘛的

```cpp
const uint32_t klen = GetFixed32(&p, limit);
```

`const` = 这个变量**读过就不许再改**。

- 后面手滑写了 `klen = 5;` → **直接编译报错**，不用等运行时才发现
- 编译器知道你不动它，可以更放心地优化

> 习惯：**所有"算出一次就不再变"的局部变量都加 `const`。** 这不是洁癖 —— 它让"这个值在哪被改了"这个问题永远不用问。

### 一条能一直用的规则

> **内存里的变量：够用就行，`int` 无所谓。**
> **要落盘、要跨机器、要进协议的东西：宽度必须钉死，`uint32_t` / `uint64_t`。**
