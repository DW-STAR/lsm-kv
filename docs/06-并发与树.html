01并发是什么

一个程序里有多条执行流同时在推进，就叫并发。

常见的两种形态：

形态共享什么怎么通信麻烦程度
多线程共享同一块内存直接读写同一个变量高（互相踩数据）
多进程 / 多机不共享发消息、socket、文件低（踩不到）

注意这个区别：麻烦不是「同时」带来的，是「共享内存 + 同时改」带来的。 两个进程各干各的、谁也不碰谁的数据，一点都不麻烦。

本质

并发 = 多个执行流同时推进。它本身不是问题，「同时改同一份数据」才是问题。

你的程序现在是什么样

单线程。main() 进去，一条道跑到黑，中间没有任何东西跟你抢数据。

所以你写 entries_.push_back(rec) 完全不用想「会不会有人同时也在 push」——不可能，只有你一个人在动它。

但 LevelDB 的 MemTable 不是这样。它要同时服务几百个读请求和一个写请求，所以它才需要跳表那套设计（第 7 节讲）。

02竞态条件

假设 x 的初始值是 0。两个线程都执行 x = x + 1。

直觉上结果是 2。但实际的执行顺序可能是这样：

时刻线程 A线程 Bx 的值
t1读 x，得到 0—0
t2—读 x，得到 00
t3算 0 + 1 = 1—0
t4—算 0 + 1 = 10
t5写 x ← 1—1
t6—写 x ← 11

结果 1。丢了一次加法。

最扎心的地方：A 没做错，B 也没做错。 单独跑任何一个，结果都对。错的是「它们交错的方式」。

这叫竞态条件（race condition）。

根源：读-改-写 不是一步

x = x + 1 在源码里是一行，在机器上至少是三步：

1. 从内存读 x 到寄存器
2. 寄存器加 1
3. 把寄存器写回内存

这三步之间，随时可能被切走。别人在这期间读到的，就是那个「旧的、还没改完的」值。

所以并发编程的核心问题只有一个：如何让「读-改-写」这一串动作，对别人来说像一个不可分割的瞬间。

这种「不可分割、中间不给别人插队」的操作，叫原子操作（atomic operation）。这个词后面会反复出现。

本质

竞态的根源是 「读-改-写」三步不是原子的。
并发编程的整部历史，就是想办法把这三步变成一步。

03加锁

最直觉的解法：动手之前先占住，别人在外面等。

心智模型就是一间屋子配一把挂锁、只有一把钥匙：

  • 拿到钥匙才能进屋（lock()）
  • 没钥匙的人在门口排队，什么都干不了（阻塞）
  • 出来把钥匙还回去（unlock()）
std::mutex m;

// 线程 A 和 B 都执行这段
m.lock();          // 占住；如果别人占着，就在这里等
x = x + 1;         // 现在保证只有我一个人在动 x
m.unlock();        // 放手

现在无论怎么交错，A 的「读-改-写」和 B 的「读-改-写」不会重叠。结果一定是 2。

三个代价

代价具体是什么什么时候致命
阻塞等锁的线程什么都干不了，纯浪费 CPU 时间片锁持有时间长（比如锁住期间做 IO）
开销加锁解锁本身要几十纳秒，还要处理缓存一致性高频短操作（比如每次加一个计数器）
死锁A 等 B 放锁，B 等 A 放锁，两个人永远等下去一个线程要同时拿两把锁时
本质

锁是悲观策略：先假设有人会来抢，所以先占住。
它用「排队的时间」换取「绝对的正确」。简单、可靠、代价是慢。

04CAS

加锁是悲观派。还有一派叫乐观派：

「先干，干完交货的时候检查一下有没有人动过。没动过就算成功，动过就重做。」

这个「检查 + 改」的动作，硬件提供了现成的一条指令，叫 CAS（Compare-And-Swap，比较并交换）。

它做什么

CAS(内存位置, 我以为是旧值, 要改成的新值)：

    如果 现在内存里存的值 == 我以为是旧值：
        内存里的值 = 新值
        返回 true          ← 成功
    否则：
        什么都不做
        返回 false         ← 有人抢先改过了

关键词是「比较」和「写入」在硬件层面是一步完成的。中间没有任何缝隙可以让别的线程插进来。这就是它原子的物理基础。

怎么用它做加法

失败就重来，循环到成功为止。这个循环有个名字叫自旋（spin）。

do {
    old  = x;                    // 读当前值
    newv = old + 1;              // 算新值
} while (!CAS(&x, old, newv));   // 如果这期间 x 被别人改过，重来

走一遍上面那个丢加法的场景：

  • A 读到 0，算好 1，CAS(0 → 1) 成功，x = 1
  • B 也读到 0，算好 1，CAS(x, 期望 0, 改成 1) —— 但 x 现在是 1，不等于期望的 0 → 失败
  • B 重来：读到 1，算好 2，CAS(1 → 2) 成功，x = 2

结果正确。而且全程没有一把锁，没有任何人阻塞。

和锁的对比

加锁CAS
策略悲观：先占住再干乐观：先干，冲突了重做
冲突时排队等重试
冲突少时慢（每次都白加一次锁）快（一次就成）
冲突多时稳（等就完了）惨（一直重试，白烧 CPU）
会不会死锁会不会（没有人持有什么）
写起来简单复杂（要想清楚每步重试）
本质

CAS 是一条 CPU 指令，把「比较」和「写入」压成一个不可分割的瞬间。
它让「改数据」不再需要排队——代价是冲突时要重做。

一个经典坑：ABA 问题

值从 A 变成 B，又变回 A。CAS 看「现在是 A，和我期望的 A 一样」，就以为没人动过——其实动过两次。
解法：不比较值，比较版本号（每改一次 +1）。知道有这么回事就够了。

05二叉搜索树与红黑树

先看二叉搜索树（BST）

规则一句话：左边全比我小，右边全比我大。

所以查找像查字典：比当前节点小就往左走，大就往右走。走到底还没找到，就是不存在。

代价是树的高度。树有多高，最坏就要走多少步。

问题：它会长歪

如果你按 1, 2, 3, 4, 5 的顺序插入：

解法：不平衡就调整

插入或删除之后，如果树长歪了，就调整节点的父子关系，把它拉回平衡。这个动作就是第 6 节的「旋转」。

两个流派：

AVL 树红黑树
平衡程度严格：左右子树高度差 ≤ 1近似：最长路径 ≤ 最短路径的 2 倍
树高更低（查找更快一点点）稍高
插入删除的调整可能要一路调整到根最多 3 次旋转就收工
用在哪读远多于写的场景通用场景，工程默认选择

红黑树靠「给节点染红染黑 + 几条颜色规则」来间接保证近似平衡。你不用背那五条规则，只要知道：它用颜色约束代替了 AVL 的严格高度约束，换来了更少的调整次数。

本质

平衡树的存在意义只有一个：把树高压到 O(log n)。
AVL 压得更狠但调整频繁，红黑树松一点但省事——工程上永远选后者的性价比。

你的猜测：set / map 底层是红黑树吗

是。而且这是标准规定的间接结果。

容器底层结构有序吗查找复杂度
std::set / std::map红黑树有序（按 key 排序）O(log n)
std::unordered_set / unordered_map哈希表无序平均 O(1)，最坏 O(n)
std::vector连续数组看你怎么放O(n)（但常数极小）

C++ 标准没写「必须用红黑树」，它只要求「插入/删除/查找都是 O(log n) + 迭代器稳定」。但能满足这个的组合里红黑树最划算，所以 libstdc++、libc++、MSVC STL 三家都用红黑树。

你打 ACM 时用 map<int,int> 觉得「自动排序好方便」——那个「自动排序」就是红黑树在每次插入后默默旋转出来的。

06旋转

旋转是不改变数据大小关系、只改变父子关系的调整动作。分左旋和右旋，互为镜像，看一个就够。

为什么旋转是安全的

看图上最下面那行：两棵树的中序遍历结果是同一个序列 x A y B z。

中序遍历（左-根-右）在 BST 上得到的就是「从小到大排好的顺序」。两个序列一样，说明所有元素的大小关系一点没变，变的只是「谁挂在谁下面」。

这就是旋转合法的全部理由：它调整的是形状，不是数据。

红黑树怎么用它

插入一个新节点（染红）
    ↓
如果违反颜色规则
    ↓
先试「变色」（改颜色不动结构，便宜）
    ↓
变色不够了 → 旋转（左旋 / 右旋 / 先左后右 / 先右后左）
    ↓
最多 3 次旋转，收工
本质

旋转 = 在不改变元素顺序的前提下，重新分配父子关系。
它是「调整树的形状」这件事唯一不破坏排序性质的做法。

07把线接上：为什么 LSM 用跳表不用红黑树

前面六个概念到这里全部合流。看这条因果链：

红黑树维持平衡 → 必须旋转 → 一次旋转要改三四个指针（A 的右孩子、B 的左孩子、y 的父亲…） → 改到一半被打断，树就是坏的 → 所以只能加锁，把整条路径锁住 → 读的人也要抢锁
跳表维持平衡 → 不旋转，靠抛硬币决定新节点有几层 → 插入只改「前驱节点的 next」这一个指针 → 一条指令就能改完 → 用 CAS 一步搞定 → 读的人永远看到完整状态，完全不用加锁

这就是「为什么 LSM 用跳表」的技术根源。

四条理由（面试按这个顺序说）

  1. 并发：读侧可以不加锁。 MemTable 是单写多读——一个写线程，几百个读线程。跳表插入用 CAS 改一个指针，读的人不需要等；红黑树旋转要锁住一大片，读的人全被堵住。
  2. MemTable 活得短，不需要严格平衡。 它几 MB 就冻结落盘了，是个短命的写缓冲，而且从不删（删除也是写墓碑）。花力气维持严格平衡，收益接近零。
  3. 底层是链表，天然能顺序遍历。 刷盘写 SSTable 时要把 key 按序吐出来，从 L0 头节点走一遍就行；红黑树中序遍历要递归或显式栈。
  4. 代码短。 红黑树插入有 4 种情况加镜像，删除更麻烦；跳表插入就是「找每层前驱 + 链表插入」。

面试话术（背这一句）

当场这么说

「MemTable 是单写多读的场景，跳表插入只需要 CAS 改前驱的 next 指针，读侧可以完全不加锁；红黑树旋转要锁住整条路径。加上 MemTable 是短命的内存写缓冲、不需要严格平衡，所以 LevelDB 选跳表。」

跳表的缺点（别只听好的）

缺点说明
缓存不友好链表跳来跳去，每跳一次基本一次 cache miss
最坏 O(n)理论上存在（连续掷出极端结果），概率极低
内存每节点平均 2 个指针，和红黑树差不多

所以准确的说法不是「跳表更好」，而是「跳表更匹配 MemTable 这个场景」。Redis 的 ZSet 也选它，理由类似。

09自测 8 题

能答上来 6 个就算过关。想不起来的回头看对应小节。

1. 并发本身有错吗？

没有。「同时改同一份共享数据」才有错。两个进程各干各的、谁也不碰谁，完全不麻烦。

2. x = x + 1 为什么会被别的线程插队？

因为它在机器上是「读 → 算 → 写」三步，不是一步。这三步之间随时可能被切走。

3. 加锁的三个代价是什么？

阻塞（等的期间什么都干不了）、开销（加解锁本身要时间）、死锁（互相等对方放锁）。

4. CAS 是什么？为什么它能替掉锁？

一条 CPU 指令：「如果内存里的值还是我以为的旧值，就改成新值」。「比较」和「写入」在硬件层面是一步完成的，中间没有缝隙给人插队。所以不需要排队占住，冲突了重试就行。

5. 按 1,2,3,4,5 顺序插入二叉搜索树，会发生什么？

树退化成一条链，高度 = 5，查找变成 O(n)。因为每个新元素都比之前所有元素大，只能一路往右下挂。

6. 红黑树和 AVL 树的区别？

AVL 严格平衡（高度差 ≤ 1），查找快但调整频繁；红黑树近似平衡（最长路径 ≤ 最短路径 × 2），调整次数少。工程上默认选红黑树，就是因为它省事。

7. 旋转为什么不破坏排序？

因为旋转前后中序遍历结果完全一样。中序遍历就是「从小到大」，序列没变说明大小关系没变，变的只是父子关系。

8. 为什么 LSM 用跳表不用红黑树？

红黑树维持平衡要旋转，旋转要改一片指针，只能加锁，读侧也被堵住。跳表靠抛硬币决定层数，插入只改前驱的一个 next 指针，一条 CAS 就完成，读侧完全不用锁。加上 MemTable 是单写多读、短命、不需要严格平衡。
