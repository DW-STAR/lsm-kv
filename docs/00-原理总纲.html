01三个物理事实，逼出了全部设计

这个项目里没有一个设计是「因为优雅」才被选中的。每一个都是被硬件逼出来的。记住这三个事实，后面所有问题你都能自己推。

物理事实逼出了什么
内存一断电就没了 必须有磁盘上的持久副本 → WAL
磁盘比内存慢 3~5 个数量级
内存 ~100ns / SSD ~100μs / 机械盘 ~10ms		 不能每次读写都碰盘 → 内存缓存 + 批量落盘
磁盘「就地改写」会留下中间态
「顺序写」比「随机写」快一个数量级以上		 只能追加写 → LSM 的全部赌注
本质

LSM 不是发明了什么新数据结构。它做的是把随机写重排成顺序写，然后接受「读变麻烦」这个代价。整个项目后面所有的复杂度，都是在还这笔账。

对比一下另一条路：MySQL 用的 B+ 树是「就地更新」—— 找到那条记录在盘上的位置，改掉它。读很快（一次树查找就够），写很慢（随机写 + 节点分裂）。

所以两类数据库的分工是清楚的：读多写少用 B+ 树，写多读少用 LSM。HBase、Cassandra、RocksDB、LevelDB、TiKV 全是 LSM。这不是偏好，是被自己的业务形态选出来的。

02只追加：唯一安全的写入方式

先看「就地改写」崩在中间会发生什么。假设日志允许按 key 定位、原地覆盖：

完整：  [name][liupei]
改写：  [name][zh       ← 写到 'h' 断电
结果：  [name][zhei]    ← 前 2 字节是新的，后 4 字节是旧的

"zhei" 这个值从来没被任何人写过。它不是旧值，也不是新值。长度字段还是原来那个，看着完全合法 —— 你重放时凭什么都判断不出这条该信还是该扔。

这不是「丢了新数据」，是凭空造出一条假数据。前者你能发现，后者你发现不了。

再看只追加：

完整：  [...历史...][name][liupei]
追加：  [...历史...][name][liupei][name][zh    ← 写到一半断电
结果：  历史完好如初，最后一条长度不够 → 认出是残的 → 丢掉

旧数据一个字节都没被动过。你付出的代价只是一条垃圾记录，而且这条垃圾你识别得出来。

抽象出来：损坏的「半径」

就地改写只追加
一次崩溃能毁掉任意一条本来完好的记录只可能是最后一条
前缀还有效吗不一定永远有效
怎么恢复无法判断，只能整段丢或整段信砍掉尾巴，前面照用
本质

WAL 的全部价值建立在「前缀永远有效」这个性质上。就地改写在物理上摧毁了它 —— 那就不再是 WAL，只是一个「可能到处是洞的文件」。

还有三条理由，一条比一条硬

① 没有历史，就没有重放。就地改写的本质是把旧值擦掉写新值，它只保留「最后状态」，不保留「变化过程」。而重放需要的是过程：先 Put name=liupei，再 Put name=liupei_v2，再 Delete name —— 按顺序走一遍，状态才重建得出来。允许覆盖，历史就没了，你手上只剩「name 现在是什么」，那不就是个普通文件吗？WAL 这个概念会消失。

所以「只追加」不是实现选项，它是 WAL 的定义性约束。

② 并发。追加写天然串行：所有写都在末尾排队，多线程只需要抢「谁先拿到末尾位置」，一个原子自增就够。就地改写要防两个线程踩同一位置，就得加锁；锁一加，复杂度上一个量级。存储里能避开锁的地方都值得避开。

③ SSD 的物理层。SSD 不能原地改一个字节。改一个 4KB page，得把整个 512KB block 读出来、擦掉、再写回去 —— 写放大 128 倍。而顺序追加正好是 SSD 最喜欢的模式。你在算法层选了只追加，在硬件层白拿一个数量级的性能。

这条要背下来

「删整个文件」是安全的，「改文件里的一个字节」是危险的。LevelDB 的 WAL 写满一个文件，不会回头清理它，而是直接开一个新的（000001.log → 000002.log）。等内存数据 dump 成 SSTable 之后，整个旧文件一起删掉。后面做 Compaction 会反复用到这条。

03WAL：先记账，再动钱

WAL = Write-Ahead Log。三个词拆开：

  • Log = 一个只往后追加的记录本，不回头改
  • Write = 写
  • Ahead = 提前、在前面 —— 这个词才是全部内容

Ahead 指的是：日志必须走在真正的数据前面。

会计用了五百年的办法

你往银行存 100 块，会计不是直接改你的余额，而是分两步：

  1. 在流水账上记一行：10-28 / 存入 / +100
  2. 然后才去改总账里的余额：1200 → 1300

为什么？因为两种账本性质完全不同。流水账只往后加，旧的每一行永远不动 —— 写到一半断电，最多最后一行没写完，前面九万行一个字节都没坏。总账是就地改写 —— 把 1200 划掉写 1300，写到一半断电，这格里是空的还是两个数字的碎片？没人知道，这笔账废了。

所以规矩是：先记流水，再动总账。断电了拿流水账从头重放一遍，总账就修好了。

数据库里的 WAL 就是把这套东西搬进机器。

对回代码

会计你的代码
流水账（只追加）wal.log — Append 只往后写
总账（改一处算一处）entries_ — 内存里「当前是什么」
先记流水再动总账WriteRecord 里 push_back 排在 flush 之后
断电后拿流水重放Load() 读回来重建

那 7 行里 entries_.push_back(rec) 排在最后不是随手排的 —— 那就是 Ahead 这个词在代码里的位置。挪到第一行，逻辑还跑得通，但名字里的承诺已经失效了。

为什么顺序不能反

做法崩在两步中间后果
先内存，后文件内存有了，盘上没有 数据永久消失，而客户端当时被告知「写成功」
先文件，后内存盘上有了，内存没有 重启 Load 一跑，数据自己回来

关键认知：内存里的东西不是数据本身，是数据的副本。entries_ 本来就是 Load 从文件读出来的。副本丢了不叫丢数据 —— 重建的成本约等于零（而且 Load 每次启动本来就要跑）。

反过来，先写内存时 push_back 成功了、write 失败了，这时客户端已经拿到「成功」，进程一死，那条记录在世界上任何地方都不存在了。没有「再来一遍」的机会，因为写它的那个人已经不在了。

还有一条更硬的工程理由

顺序反了，你就必须实现回滚（写内存成功、写文件失败 → 得 pop_back 掉）。回滚要保证「退回去之后跟没发生过一模一样」，在并发下几乎必然写错。
顺序对了根本不需要回滚：文件写失败，内存压根没动，直接返回错误，状态是干净的。

好设计的标志，常常不是「考虑得更周全」，而是「根本不需要补救」。

04格式：让字节说清自己

一条记录在文件里长这样（小端）：

┌──────┬────────────┬──────────┬────────────┬───────────┐
│  1B  │     4B     │  klen B  │     4B     │  vlen B   │
│ type │   key长度   │   key    │ value长度   │   value   │
└──────┴────────────┴──────────┴────────────┴───────────┘

为什么必须是「长度前缀」

最直觉的做法是用分隔符，比如换行符。但 value 里完全可以包含换行符 —— 用户存一首诗，你的格式当场崩掉。

用长度前缀就没有这个问题：长度是一个定长的数字，对内容完全透明。value 里有多少个 \n、多少个 \0 都不影响切分。这是所有二进制格式（Protobuf、Thrift、Parquet）的共同选择。

为什么 type 必须是独立字段

这个项目早期用 value == "__DELETED__" 来判断删除。想一下：如果用户真的要存 "__DELETED__" 这个字符串呢？

读回来会被当成「已删除」，数据凭空消失。这不是写法问题，是格式设计问题 —— 一条记录里必须有独立字段说明「这是存还是删」，而不是靠 value 的取值去猜。

本质

用取值去猜语义，迟早会撞上「那个取值本身也是合法数据」的那天。语义要占独立的位，不跟数据抢地方。

为什么内存结构要和磁盘结构同构

磁盘上是 [type][keylen][key][vallen][value]，内存里也应该是 {type, key, value} 三个字段。

如果内存里只有 {key, value}（type 丢了），那 Load 时就得把 type 压扁成一个特殊字符串 —— 每次转换都要做一次翻译，而翻译就会有信息损失。你之前那个 __DELETED__ 的 bug，根子就是这个不同构。

两边同构之后，来回搬不需要翻译。这看起来是小事，实际上是「格式设计是否自洽」的分水岭。

05三层缓冲：数据到底停在哪

你以为「写完文件了」，其实数据离磁盘还有两道关。

层谁在管怎么进去的崩了会丢吗
① 用户态缓冲你的进程（ofstream 对象内部） write() 只是把字节拷进来 进程被杀就丢
② 内核页缓存操作系统 flush() 触发真正的 write(2) 断电 / 系统崩就丢
③ 磁盘介质硬件 fsync() 才推到这里 不会丢
一句话分清

flush() 挡的是「进程被 kill -9」，fsync() 挡的是「断电」。两者防的不是同一件事。

为什么要缓冲？因为每次进内核都要保存现场，一个字节一个字节地写会慢几百倍。操作系统还会帮你合并、排序、减少寻道 —— 这些优化都建立在「攒一批再发」之上。

代价就是：攒着的这段时间，数据是脆的。

为什么不一上来就 fsync

机械盘一次 fsync 要 5~10ms。每条写都 fsync，吞吐直接掉到几百 TPS。LevelDB 把这个做成参数（sync = false 是默认值），靠操作系统的刷盘策略兜底。

「性能 vs 安全」的取舍点，具体就落在这一行代码上。面试里问「你的 WAL 保证不丢吗」，标准答案是「我不保证，工业界默认也不保证，只有显式 sync 才保证」。

代码里哪一行对应哪一层

std::string encoded = Encode(rec);   // ① 内存（你的堆），跟文件无关
out_.write(...);                     // ② 内存 → ofstream 的用户态缓冲区
out_.flush();                        // ③ 缓冲区 → 内核页缓存（发系统调用）
entries_.push_back(rec);             // ④ 内存（你的堆）
这句最反直觉

「写磁盘」在你的代码里没有对应的行 —— 因为那一步不在你的进程里发生。你只能「请求」它发生（flush），不能「确认」它发生（那是 fsync）。

06校验：长度检查为什么不够

假设一块用了三年的 SSD 上，某个字节从 'p' 变成了 'q'：

磁盘上：[01][04 00 00 00]['n']['a']['m']['e'][06 00 00 00]['l']['i']['u']['q']['e']['i']
                                                              ↑ 这个字节坏了
Decode：长度字段全对 → 边界检查全过 → 返回 true
你的程序：读出一个「正常」的 value —— 但内容已经错了

全程没有任何一行代码报错。

你的 Decode 只检查「长度会不会超出缓冲区」。它保证的是结构没崩，保证不了内容没变。

存储里最坏的一类错

静默错误（silent corruption）：不是崩，是崩了还告诉你一切正常。用户三个月后发现数据不对，你连是哪一步坏的都查不出来。

CRC32 是什么

给每段字节配一个指纹。写的时候算一遍存进去，读的时候重算一遍对比。相等 → 内容没被动过；不等 → 这条坏了。

数学上：把整串字节看成一个巨大的二进制多项式，除一个固定的生成多项式，余数就是 CRC。模 2 除法里没有进位，减法和加法都等于异或 —— 所以整个算法只有 移位 和 异或，没有乘除。

错误类型能否检出
任何 1 位错一定检出
任何 2 位错一定检出
长度 ≤ 32 位的连续出错一定检出
其他情况漏检概率 2⁻³² ≈ 23 亿分之一

注意：CRC 只能检测，不能修复。发现坏了只能丢。修复要靠副本或纠删码，那是另一个量级的东西。

为什么和字符串哈希不一样

哈希表用的 hashCRC32
目的把 key 分散到桶里判断字节有没有被改过
碰撞了怎样无所谓，桶里再比一次，只是慢一点检测失效，坏数据被当成好的
有没有保证没有，靠统计经验有数学结构，边界可证明

所以 CRC 不能只是「随便搅一搅」，它必须是真正的余数。正因为是余数，才有上面那张表的保证。哈希函数给不出这种承诺。

为什么查表

朴素做法：每个字节做 8 轮「看最低位 → 右移 → 条件异或」。1 MB = 800 万轮。

但一个字节只有 256 种可能。「某个字节走完 8 轮会得到什么」是固定答案，跟前面的数据无关 —— 那就预先全算出来存着。之后每个字节只需要：查一次表 + 两次异或。

每字节省额外内存
逐位算8 轮位运算0
查表1 次查表 + 2 次异或1 KB
原型

空间换时间最经典的案例，也是你以后会反复遇到的原型。AES 的 S-box、Base64 的编码表、UTF-8 解码表、大小写转换表 —— 全是同一个套路：把「按规则算」换成「查预先算好的结果」。

有一个数字要记住

你的实现实测 400 MB/s（8 MiB / 20 ms）。换算一下：校验 1 GB 的 WAL 要 2.5 秒。

这就是为什么真实系统不让 WAL 无限长 —— 涨到一定大小就得把内存 dump 成 SSTable，然后日志截断重开。否则重启越来越慢，最后要几分钟。

因果关系

SSTable 那套东西存在的第一个理由，就是这个 2.5 秒。不是为了「架构好看」，是因为不这么做启动会变得无法接受。

07这套东西会长成什么

你现在有的只是最底层的一环。完整的 LSM 是这么长出来的 —— 每一步都在解决上一步暴露的问题，同时又引入一个新问题。

组件解决什么引入什么新问题
追加日志
你现在这里		 不丢数据 重启要全量重放，日志越长越慢
MemTable
内存里有序的结构（跳表）		 读不用扫全日志，内存里直接找 内存有限，装不下
SSTable
内存写满就 dump 成有序文件		 内存腾空，日志可截断，重启只重放剩下的 文件越来越多，读要查很多个文件
Compaction
把多个 SSTable 合并		 文件数降下来，删掉被覆盖的旧值 写放大 —— 合并本身要重写数据
Bloom Filter 查一个不存在的 key 时，不用真的去翻每个文件 多占一点内存，有一定误判率
Block Cache 热数据别每次都读盘 又占内存，还要做淘汰策略（LRU）
整条链的本质

LSM 的每一个组件，都是在「写放大 / 读放大 / 空间放大」这个三角里换位置。没有免费的午餐，只有选哪个贵。
你优化任何一项，另外两项几乎必然变差 —— 这就是为什么数据库有几十个可调参数。

08三种放大（面试必问）

名称定义典型来源
写放大
write amplification		 一次逻辑写，实际导致多少次物理写 Compaction 反复重写数据。最坏情况下一条记录在每一层都被重写一遍
读放大
read amplification		 一次逻辑读，实际要碰多少个文件 / 多少层 层数越多，一层层往下查的次数越多
空间放大
space amplification		 磁盘占用 ÷ 实际数据量 被覆盖的旧值和墓碑还没被 Compaction 清掉

三者此消彼长。举两个极端：

  • 层数少（比如只有 2 层）→ 读放大低（查的文件少），但每层数据多，Compaction 一次要重写的量巨大 → 写放大高
  • 层数多（比如 7 层）→ 每层数据小，Compaction 便宜 → 写放大低，但读要一层层找 → 读放大高

LevelDB 默认 7 层，每层容量是上一层的 10 倍。这个「10 倍」就是调参的核心旋钮。

09B+ 树 vs LSM：为什么不用 MySQL 那一套

B+ 树（MySQL InnoDB）LSM 树（LevelDB / RocksDB）
写入方式就地更新：找到位置，改掉只追加：写新记录，旧的作废
写性能慢（随机写 + 节点分裂）快（顺序写）
读性能快（一次树查找）慢（可能要多层查）
空间紧凑，无冗余有冗余（旧版本要等合并才清）
适合读多写少（订单、账务）写多读少（日志、时序、消息、监控）

这不是「谁更先进」，是业务形态选出来的。银行转账一天几百万笔但查询上亿次，选 B+ 树；埋点数据一天写几十亿条但很少按单条查，选 LSM。

面试官问「为什么不用 B+ 树」，标准答法是：「我的场景是写密集，B+ 树每次写都是随机 IO，在 SSD 上会触发写放大；LSM 把随机写转成顺序写，代价是读要多层查找，用 Bloom Filter 和缓存来缓解。」

10面试怎么讲（3 分钟结构）

第一句：定位

「我用 C++17 从零写了一个 LSM-Tree 的 KV 存储引擎，核心是追加日志 + 有序文件，写路径全部是顺序 IO。」

注意这句里没有一个形容词。「高性能」「优雅」这类词一个都不要，全是可被追问的空话。

  1. 只追加 + WAL
    往下钻：为什么不能就地改？→ 中间态不可判定，破坏半径从「最后一条」变成「任意一条」。
    再往下：为什么顺序不能反？→ 反了要写回滚，回滚在并发下几乎必错。
  2. 记录格式
    往下钻：为什么用长度前缀不用分隔符？→ value 里可能有任意字节。
    再往下：为什么 type 要独立字段？→ 用取值猜语义，迟早撞上「那个取值本身也是合法数据」。
  3. CRC 校验
    往下钻：长度检查为什么不够？→ 只保证结构不崩，保证不了内容没变，静默错误最致命。
    再往下：为什么查表？→ 空间换时间，1 KB 换 8 倍，而且这个模式在 AES/Base64 里到处都是。

一个数字

「CRC32 实测 400 MB/s，也就是校验 1 GB 的日志要 2.5 秒 —— 这个数字就是我后面要做 SSTable 和 Compaction 的动机。」

能主动给出「我这个数字导致了什么设计决策」，比背十个概念有用。这是「有对比数据」和「只顾代码量」的分界线。

一个取舍

「LSM 的代价是读放大。我接受它，因为我的场景写远多于读；如果是读密集场景，B+ 树更合适。」

面试时的红线

说不出「另一条路是什么、代价是什么」，就等于没做过。任何设计问题，先讲备选方案，再讲你为什么没选它。

12如果只能记五句话

  1. 内存是副本，磁盘是原件。副本丢了重建，原件没了就是没了。所以先改原件。
  2. 只追加不是选择，是前提。它保证「前缀永远有效」，而这正是重放能成立的全部原因。
  3. WAL = 先记账，再动钱。崩了照账重来。顺序反了你就得写回滚，那比重放难十倍。
  4. 长度检查保结构，校验和保内容。静默错误比崩溃致命，因为崩溃你会知道。
  5. LSM 的本质是把随机写换成顺序写，代价是读变麻烦。所有的组件都在还这笔账。
