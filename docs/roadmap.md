# 12 周路线

按每晚 1.5 小时 × 每周 6 天（约 9 小时/周）估算，总计约 105 小时。

**开始时间**：考研初试（2026-12-19 ~ 20）结束之后。
考前这两个月只做第 1 周的内容，不要往后推进。

每一周的结尾都必须有一句**你能说出口的话**（"周末该能回答"那一栏）。
说不出来，就是这一周没做完，不要往后走。

---

## 第 1 周 · 地基

**做什么**
- WSL2 + Ubuntu + 工具链（g++ / cmake / git / gdb）
- 读懂 `Slice`、`Status`、`DB` 三个头文件
- 编译跑通内存版，看懂 `cmake -S . -B build` 在干什么

**产出**：环境可用，`./build/lsmkv_test` 打印 `all tests passed`

**周末该能回答**
- `Slice` 相比 `std::string` 省掉了什么开销？它有什么生命周期陷阱？
- 存储引擎为什么不用异常做错误处理？
- `DB::Open` 为什么要用 `DB**` 而不是返回 `DB*`？

---

## 第 2 周 · 变长编码 + WAL 写入

**做什么**
- varint / fixed32 编解码（`util/coding.{h,cpp}`）
- 日志记录格式：`type | length | crc32 | payload`
- 改造 `Put`：**先写 WAL，再写内存**

**产出**：`wals/writer.cpp`，跑一次 Put 后磁盘上出现一个 `.log` 文件

**周末该能回答**
- 为什么每条日志要带 CRC 校验？
- 为什么先写日志再写内存表，而不是反过来？
- 为什么用变长编码而不是固定 4 字节存长度？

---

## 第 3 周 · WAL 崩溃恢复

**做什么**
- 日志读取器：从头重放，遇到校验失败就停止
- 写一个"写一半就被 kill"的测试（写进程 + `kill -9`）
- 重启后能把已确认的数据全部恢复

**产出**：`wals/reader.cpp` + 一个真正能过的崩溃恢复测试

**周末该能回答**
- 如果最后一条日志写了一半（长度字段 4 字节只写了 2 字节），你怎么处理？
- CRC 校验失败的记录，应该跳过还是直接报错？为什么？
- 为什么"只截断，不修补"是安全的？

---

## 第 4 周 · 手写 SkipList

**做什么**
- 从零写跳表：插入、查找、删除（删除用标记位，不做物理删除）
- 随机层高 + 最大层数限制
- 写单测：随机插入 10 万个 key，验证有序性和查找正确性

**产出**：`memtable/skiplist.h`

**周末该能回答**（这一周面试问得最狠）
- 跳表查找的期望时间复杂度是多少？怎么推的？
- 为什么 LevelDB 用跳表而不是红黑树？（三个理由：实现简单、范围查询天然友好、并发加锁粒度小）
- 跳表的层高为什么用随机数？期望层高是多少？
- 跳表的空间复杂度？

---

## 第 5 周 · MemTable 封装

**做什么**
- 用跳表包一层 `MemTable`，对外提供 `Add` / `Get` / `NewIterator`
- key 的内部编码：`user_key | sequence_number | type`
- 内存占用估算 + 写满后冻结成 Immutable MemTable

**产出**：`memtable/memtable.{h,cpp}`

**周末该能回答**
- 为什么内部 key 要拼上序列号？（提示：同一个 user key 的多个版本）
- 删除操作为什么要写"墓碑"而不是真删？
- "冻结"这一步解决的是什么并发问题？

---

## 第 6 周 · SSTable 写入

**做什么**
- Block 格式：数据区 + 重启点（restart points）前缀压缩
- Table 格式：`data block | ... | index block | footer`
- 把 Immutable MemTable 刷写成 `.sst` 文件

**产出**：`table/table_builder.{h,cpp}`，磁盘上出现第一个 `.sst`

**周末该能回答**
- Block 里的"重启点"是干什么的？它换来什么、付出什么？
- 为什么 index block 只需要存每个 block 的最后一个 key？
- Footer 里为什么要放 magic number 和格式版本？

---

## 第 7 周 · SSTable 读取 + Block 索引

**做什么**
- 打开 `.sst`：读 footer → 读 index block → 定位 data block
- Block 内的二分查找
- 迭代器：能在整个表上顺序遍历

**产出**：`table/table.{h,cpp}`，能读出第 6 周写进去的数据

**周末该能回答**
- 在一个 SSTable 里查一个 key，一共要读几次磁盘？怎么把这个次数降到 1？
- Block 内部的查找为什么可以二分？（提示：重启点）
- 如果 `.sst` 文件被截断了一半，你怎么检测出来？

---

## 第 8 周 · 布隆过滤器

**做什么**
- 布隆过滤器：`k` 个哈希函数 + 位数组
- 写入时生成 filters，查询时先过滤
- 调参：给定误判率，怎么算需要的位数和哈希个数？

**产出**：`util/bloom.{h,cpp}`，并接进读路径

**周末该能回答**
- 布隆过滤器能不能有假阴性？为什么？
- 误判率 1% 时，每个 key 大约需要多少 bit？
- 为什么布隆过滤器是"读放大"问题的关键一环？

---

## 第 9 周 · 多级查找路径

**做什么**
- 读路径串起来：MemTable → Immutable MemTable → L0 逐文件 → L1+ 二分定位
- 版本合并：同 key 取序列号最大的
- 一个完整的 `DBImpl::Get`

**产出**：`db/db_impl.cpp`，能查到落在任意层的数据

**周末该能回答**
- 一次读操作最多要碰几个文件？为什么 L0 要逐个查而 L1+ 可以二分？
- 为什么 L0 的文件之间 key 范围会重叠？

---

## 第 10 周 · Compaction

**做什么**
- 分层策略：L0 → L1 → L2 …… 每层大小按倍数增长
- 归并排序式合并 + 丢弃被覆盖的版本 + 真正物理删除墓碑
- 元数据管理：MANIFEST + VersionEdit

**产出**：`db/version_set.{h,cpp}`、`db/compaction.{h,cpp}`

**周末该能回答**
- 为什么 LSM 叫"写放大换读放大"？放大倍数怎么算？
- Compaction 什么时候触发？在哪几个时机？
- 合并过程中如果进程被 kill，怎么保证不丢数据、不损坏？

---

## 第 11 周 · 缓存 + 迭代器

**做什么**

**产出**：`util/cache.{h,cpp}`、`db/merging_iterator.{h,cpp}`

**周末该能回答**
- LRU 用哈希表 + 双向链表实现，两个操作各是多少复杂度？
- 缓存分片解决什么竞争问题？
- 合并迭代器怎么处理"同一个 key 在多个层都存在"？

## 简历该怎么写（第 12 周用）

> **LSM-Tree 键值存储引擎**（C++17 / Linux，个人项目，约 6k 行）
> 从零实现一个支持持久化的嵌入式 KV 存储引擎，写入吞吐 X MB/s，随机读 P99 延迟 Y μs。
> - 设计 WAL 预写日志 + CRC 校验，支持进程被 kill -9 后的完整崩溃恢复；
> - 基于 SkipList 实现 MemTable，内部 key 编码 `user_key|seq|type` 实现多版本语义；
> - 实现 SSTable 格式（Block + 重启点前缀压缩 + 二级索引）与布隆过滤器，
>   将不存在 key 的查询从 O(文件数) 降到 O(1)，随机读延迟下降 Z%；
> - 实现分层 Compaction 与 MANIFEST 版本管理，控制写放大与读放大的平衡。

**注意**：上面每一个百分号和数字，都必须是你自己压出来的。编的数字在面试里撑不过三个追问。
