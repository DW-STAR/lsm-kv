01

先把词认全

你说这些词看不懂 —— 那就先把词说完。这张表里的每个词，后面都会在代码里出现。看不懂名字是无法理解代码的。

词英文全称一句话定义
MemTablememory table内存里那张正在接收写入的表。进程一退，它就没了。
SSTableSorted String Table磁盘上那个按 key 排好序的文件。写完就不再改。读作「S-S-table」。
落盘flush / persist把内存里的数据写到磁盘上。不是"拷过去"，是"保证断电也不丢"。
Recordrecord一条记录：key + value + type（是写入还是删除）。
Encode / Decode—把 Record 变成一串字节 / 把一串字节还原成 Record。两个必须成对。
CRC32Cyclic Redundancy Check一段字节的「指纹」。内容改了一个 bit，指纹就完全不同。用来发现"东西坏了"。
footer—文件最后的一小段固定长度的区域，记着"数据到哪结束"。中文叫「文件尾」。
offset—偏移。从文件开头数，是第几个字节。从 0 开始数。
seek—把读位置直接跳到第 N 个字节，中间的不读。像唱片机直接落针。
magic number—一个约定好的常数，写在文件里，用来确认"这确实是我的文件"。中文叫「魔数」。
迭代器iterator一个「位置」。它不拥有数据，只是握着"我现在站在哪个节点上"。
墓碑tombstone一条 type = kDelete 的记录。删除不是抹掉，是写一条"这个 key 死了"的公告。
compaction合并把多个 SSTable 合成一个，顺便扔掉墓碑和被覆盖的旧值。中文叫「合并」或「压缩」。
稀疏索引sparse index每 N 条记录才记一个「key → offset」。查询时先在索引里二分，再进文件读一小段。
block块SSTable 内部按 4KB 切出来的小段，每段自带校验。跳过一个坏块不用把整个文件读废。
记忆锚点：这一页只有两个词是主角 —— MemTable（内存，会没）和 SSTable（磁盘，不会没）。其他 13 个词都是为了让"从内存搬到磁盘"这件事可靠而存在的。
02

为什么要有这个文件

术语：MemTable 是内存表。

定义：它是一张包着 SkipList 的壳，所有写入先落到这里。它活在进程的堆上。

问题：进程一退出、机器一断电、或者被 kill -9，这块内存就归还给操作系统了。里面的数据一个字节都不剩。

你在 Week 2 已经解决过一半：WAL（预写日志）。每写一条先追加到 wal.log，崩溃了重放一遍就能把内存表重建出来。

但 WAL 有个性质：它是按时间顺序追加的，一个 key 可能在里面出现十次（十次修改），而且越老的在越前面。用它查一个 key，你得从头翻到尾，还得自己判断哪条最新 —— 几百万行就是一秒多。

所以还需要第二种东西：把内存表整整齐齐地倒出来，一个 key 只留最新那条，并且按 key 排好序。这个东西就是 SSTable。

wal.log（Week 2 已有）

  • 按时间顺序追加
  • 同一个 key 出现多次
  • 查一个 key 要扫全文件
  • 用途：崩溃恢复

000001.sst（今天要做）

  • 按 key 排好序
  • 一个 key 只有一条（最新的）
  • 查一个 key 可以二分
  • 用途：长期存储 + 查询

比喻（落在具体代码上）：WAL 像流水账 —— 按时间记账，想知道某个账户现在多少钱，得从头翻到最后。
SSTable 像整理好的账本 —— 按账号排序，一翻就到。它们记的是同一笔钱，但一个是过程，一个是结果。

一句话：WAL 保证"不丢"，SSTable 保证"查得快"。两个都要，缺一不可。
03

文件长什么样

先看结论，再逐字节拆。整个文件 89 个字节，分两大块：

┌──────────────────────────────────────┐ 偏移 0
│ record 0   21 字节   apple = red      │
│ record 1   25 字节   banana = yellow   │  ← 数据区（data）
│ record 2   19 字节   cherry = 墓碑     │     共 65 字节
├──────────────────────────────────────┤ 偏移 65 = data_end
│ data_end    8 字节   = 65              │
│ count       8 字节   = 3               │  ← footer（固定 24 字节）
│ magic       8 字节   = LSMSST01        │
└──────────────────────────────────────┘ 偏移 89

下面这 89 个格子就是这个文件真实的字节。点任意一个格子，右边会告诉你它是什么。

000001.sst · 89 byteshex / ascii
record 0（apple） record 1（banana） record 2（cherry 墓碑） footer
点左边任意一个字节。

每一格是 1 个字节，上面是十六进制，下面是它对应的字符（不可打印的显示成 ·）。

同一个字段的几个字节点哪个都一样 —— 它们属于同一个东西。

一条记录固定是这六段

三段 record 的内部结构完全一样，都是 record.h 里 Encode() 拼出来的顺序：

顺序字段长度作用
1CRC4 字节后面 5 段的指纹。读的时候重算，对不上就是内容坏了。
2type1 字节1 = 写入，2 = 墓碑（删除）。
3klen4 字节key 有多长。没有它，读的时候就不知道 key 到哪儿结束。
4keyklen 字节原样存放，不加密、不加结束符。
5vlen4 字节value 有多长。墓碑这里是 0。
6valuevlen 字节原样存放。
为什么先放 CRC，不放到最后？
读的时候，你得先有一个"预期值"，才知道后面那段该校验成什么。放最后的话，你得先把整条解析完、找到末尾，才拿到 CRC —— 而末尾的位置又依赖前面的长度字段，可长度字段本身可能是坏的。
先拿到校验值，再校验内容。顺序反了，整个机制立不起来。

为什么长度字段写 4 个字节

看 record 0 的 klen：字节是 05 00 00 00，读出来是 5。

这就是「小端序」（little-endian）：低位字节放在前面。x86 的 CPU 天然就是这个顺序，所以 memcpy 一个 uint32_t 进去，字节序不用管。

record.h 里那两个函数就是干这个的：

inline void PutFixed32(std::string* dst, uint32_t v) {
  char buf[4];
  std::memcpy(buf, &v, 4);   // 把 4 字节整数原样抄进缓冲区
  dst->append(buf, 4);
}

4 个字节最大能表示 40 亿。key 不可能那么长，但长度字段宁可宽一档，不要刚好够用 —— 32 位在"算着算着就溢出"的时候是静默出错，多 4 个字节的成本几乎为零。

04

怎么写进去

术语：SSTableBuilder，写文件的那个类。

定义：它是一个「边来边写」的东西。你给它一条记录，它编码成字节、追加到文件末尾、记下偏移。

为什么不能一次性传一整个数组：因为上游是 MemTable 的迭代器，数据是一条一条来的。要收集成一个数组再写，等于在内存里又存了一份 —— 那张表本来就是因为太大才要落盘的。

Add：一条记录进来发生什么

  1. 检查文件开着没 —— 没开就报错。关掉的 FILE* 再写一次是未定义行为。
  2. 检查顺序 —— record.key <= last_key_ 就拒绝。这是今晚最重要的一行。
  3. 编码 —— 调 Encode(record)，拿到那 21 个字节。
  4. 写文件 —— fwrite，然后检查返回值是不是真的写完了。
  5. 记账 —— offset_ += 字节数，++count_，last_key_ = record.key。

第 2 步为什么能单独拿出来说？看这两种写法：

// 有守卫
if (count_ > 0 && record.key <= last_key_)
  return Status::InvalidArgument("sstable: key order violated");

// 没有守卫
// 什么也不写，直接 fwrite

没有守卫的那个版本：文件照样写得成功、照样读得回来、测试照样全绿。唯一的症状是某几个 key 查不到，而且只在大数据量下出现 —— 因为破坏的是二分和归并的前提，而它们不会报错，只会给出错误答案。

宁可写失败，不要写出一个静默错误的文件。
这条原则在存储里没有例外。一个"看起来正常、实际错乱"的文件，比一个明确报错的文件危险一百倍 —— 因为它会被放进生产环境，然后三个月后炸。

Finish：收尾才有"完整"

  1. 拼 footer —— data_end、count、magic，三个 8 字节，一共 24。
  2. 写进去 —— 追加到数据区后面。
  3. 三层都刷 —— fflush 把用户态缓冲交给内核，_commit/fsync 把内核 buffer 推给设备，最后 fclose。
  4. file_ = nullptr —— 立刻置空。

第 3 步为什么要刷三层？因为「写进文件」这句话有四种含义，你只做到前两层的时候，断电就全没了：

你的 std::string
   ↓ fwrite
C 库的缓冲区（4KB，用户态）
   ↓ fflush
操作系统的 page cache（内核态）
   ↓ fsync / _commit        ← 只有走到这一步，才叫"落盘"
磁盘设备

第 4 步为什么要立刻置空？不置空的话，后面误调 Add 会往一个已关闭的 FILE* 上写 —— 可能崩，也可能"成功"写进一块已经不属于你的内存。悬空指针的定义就是这样：指针还在，指向的东西已经没了。

一个刻意的设计：没调 Finish 就析构，这个文件不补 footer，于是打开时必然报 Corruption。
这是故意的 —— 半成品绝不能长得像好文件。要么整份交出去，要么明确作废，没有中间状态。
05

怎么读回来

术语：SSTable::Open。

定义：打开一个已有文件，把它变成一个能查询的对象。

问题：你手里只有"这个文件多长"，完全不知道里面有什么。数据在哪结束？不知道。索引在哪？不知道。

所以只能从末尾开始读。因为文件最后 24 个字节永远是 footer —— 这个位置不依赖任何前置信息，只要知道文件总长就能算出来：

// 文件 89 字节，footer 24 字节
// footer 起点 = 89 - 24 = 65
const char* p = data.data() + data.size() - kFooterSize;
data_end_ = GetFixed64(&p, limit);   // 65  ← 现在知道数据区在哪了
count_    = GetFixed64(&p, limit);   // 3
magic     = GetFixed64(&p, limit);   // 0x4C534D5353543031

拿到 data_end 之后，[0, 65) 就是数据区，从偏移 0 一路 Decode 下去就行。

为什么 footer 必须定长
因为"从后往前退 N 字节"这个动作，必须知道 N。
如果 footer 变长，你就得先读一个头才知道 footer 在哪 —— 而头的位置又要先读 footer。死循环。
所有"从末尾往回读"的格式，尾巴都必须定长。

magic 是干嘛的

0x4C534D5353543031 就是 ASCII 的 "LSMSST01"（小端存进去，所以你在 hex 里看到的是反过来的 31 30 54 53 53 4D 53 4C）。

它挡的是「有人把 wal.log 或者一张图片当成 SSTable 打开」。没有它，那种误用会表现成一堆莫名其妙的 corruption 错误，很难查。有了它，第一句话就能说清"这不是我的文件"。

一个必须记住的顺序：
读 footer 之前，必须先检查文件长度 ≥ 24。
文件只有 10 个字节时，data.data() + size - 24 会算到缓冲区前面去 —— 那不是"读到垃圾"，是直接越界（未定义行为）。
所有"从末尾往回退 N 字节"的代码，前面都必须有一句 size >= N。
06

有序值钱在哪

这是整个 SSTable 里唯一真正重要的性质。「Sorted」那两个字不是格式的装饰，是这个数据结构存在的理由。

好处一：查一条不用扫全表

文件有序，就可以每 N 条记一个 key → offset 的锚点（稀疏索引）。查 pear 时先在锚点里二分找到 [mango, peach] 那一段，然后只读那 4KB。几万条记录 → 一次读取。

文件乱序，这个办法直接失效 —— 你只能从头扫到尾。

好处二：合并两个文件不用建哈希表

两个文件都有序，合并就是「两边各伸一个手指，谁小谁往前走」：

文件 A: apple  banana  mango
文件 B:        banana  cherry
              ↓ 对撞
结果  : apple  banana(选新的)  cherry  mango

只用两个指针，内存 O(1)。这就是 compaction 的全部原理，几百万条也一样。

好处三：同一个 key 的新旧版本必然挨着

合并的时候，同一个 key 的两条记录一定前后相邻，谁新谁旧一目了然 —— 取后面那条，扔掉前面那条。不用时间戳，不用额外字段。

但「有序」是你要自己守住的，格式不替你保证。
Add 里那一行 if (count_ > 0 && record.key <= last_key_) return ... 就是守门人。
去掉它，上面三个好处全部失效，而没有任何东西会报错。

比喻（落在代码上）：有序的 SSTable 像按拼音排好的字典 —— 查「张」字只要翻到 Z 那一叠。无序的 SSTable 像把字典的每一页撕下来打乱 —— 字一个不少，但你只能一页页找。

07

现在还缺什么

今晚这版 SSTable 有个刻意的缺口：没有索引。

Open 把整个文件读进内存，Get 在整块内存上从偏移 0 开始线性扫。真实引擎里完全不能接受 —— 一个 SSTable 可能几百 MB，每查一条扫全文件。

我实测过这笔代价（demo_sstable 的 [6]）：

记录数文件大小200 次查询平均单次
5,000170 KB342 ms1.7 ms
40,0001.4 MB2586 ms12.9 ms

数据量 8 倍，耗时 7.6 倍 —— 标准的 O(N)。一次查询 13 毫秒，这不是 bug，是缺索引。

为什么明知慢还这么写？因为今晚要验证的不是性能，是字节格式：

先把数据搬对，再谈怎么少搬。
顺序反了会同时抓两只兔子 —— 格式还没对就开始优化，最后两边都说不清是哪里出的问题。

下次要做的三件事：

步骤做什么把什么变成什么
① 索引每 N 条记一个 (key, offset)，放在 footer 前面O(N) → O(log N + 4KB)
② 分块数据按 4KB 切，每块自带校验坏一块只废一块，不用整文件报错
③ 按需读只 seek + 读需要的那几 KB内存从 O(文件大小) → O(1)
