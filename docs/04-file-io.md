## 0. 从零：先把六个词讲清楚

在碰任何 API 之前，这六个词必须先落地。**它们不是 C++ 的东西，是操作系统的东西 —— C++ 只是给它们套了一层壳。**

### 0.1 文件 = 一段有名字的字节

你以为文件是"文档"。不是。

**文件就是磁盘上一段连续的字节，有个名字，有个长度。** 就这些。没有行、没有列、没有字段、没有类型。

你用记事本打开 `wal.log` 看到乱码，是因为**记事本替你做了翻译** —— 它假设这些字节是字符编码，然后去查表。可你写进去的字节根本不是字符，是「类型 1」「长度 4」「字母 n」。

**文件自己不知道自己是文本还是二进制。只有打开它的程序知道。**

### 0.2 「打开文件」到底发生了什么

你的程序跑在**用户态**，磁盘归**内核**管。程序不能直接碰磁盘。

所以流程是：

```
1. 你告诉操作系统：打开 D:\code\lsm-kv\wal.log，我要写
2. 内核检查权限、找到文件、在内核里建一条记录
3. 内核给你一个编号 —— 这叫「文件句柄」
      Windows 叫 HANDLE，Linux 叫文件描述符（fd），都是个小整数，比如 3
4. 之后你所有读写都是「往 3 号句柄操作」，由内核替你真正干活
```

`std::ofstream` 这个对象里装的就是三样东西：

| 装着什么 | 作用 |
|---|---|
| 那个句柄 | 告诉内核"我说的是哪个文件" |
| 一块缓冲区 | 攒够一批再交给内核（省系统调用） |
| 一个**位置** | 下次读写从第几个字节开始 ← **重点，见 0.3** |

这就是为什么必须有 `close()`：**不关，这个编号就一直被占着不还。**

### 0.3 「位置」= 你 Decode 里的那个 `p`

每个打开的文件都有一个**当前位置**，记录"下次读/写从第几个字节开始"。

初始值取决于打开模式：

| 打开方式 | 初始位置 |
|---|---|
| 普通打开 | 0（文件开头） |
| `app` | 文件末尾 |
| `ate` | 文件末尾（但之后可以往回走） |

**这跟你 `Decode` 里的游标 `p` 是同一个东西。** 唯一的区别是：

| | 谁负责把位置往后挪 |
|---|---|
| 你 `Decode` 里的 `p` | **你自己** —— 写了 4 次 `p += klen` |
| 文件流的「位置」 | **库替你** —— 每次 `read`/`write` 完自动挪 |

**记住这一条，下面 `while` 的疑问就自然解开了。**

### 0.4 副作用：函数不只是「返回值」

一个函数除了给你返回值，还可能**改变外部世界**。这叫**副作用**。

```cpp
int x = 0;
int y = f(x);      // 调用完之后，x 还是 0 吗？
```

答案取决于 `f` 怎么写的：

```cpp
int f(int v) { return v * 2; }        // x 不变（传的是副本）
void g(int* p) { *p = 5; }            // 如果调的是 g(&x)，x 变成 5
```

**光看 `f(x)` 这一行，你判断不出 x 会不会变。** 必须看函数实现或者文档。

`read()` 的返回值是「流对象本身」（所以能直接放进 `while` 条件），但它真正干的活有两件：

1. 从当前位置拷贝 n 个字节到你的缓冲区
2. **把位置往后挪 n** ← 这是副作用

**所以循环体里什么都不用写。** 因为 `read` 这个**调用本身**已经在改变状态了，不需要你在 body 里再动什么。

### 0.5 返回值能不能当「真假」用

`read` 返回的是 `std::ifstream&`（流的引用），不是 `bool`。

那为什么能写在 `while (...)` 里？

因为 `std::istream` 定义了**到 bool 的隐式转换**，规则是：

> 「上一次操作成功了吗？」

成功 → `true`，失败 → `false`。所以 `while (in.read(...))` 读作：

> **「只要上一次读成功了，就继续。」**

（C++11 之前用的是 `operator void*`，现在用的是 `explicit operator bool`。你要知道的是：**它能当条件用，含义是"上次操作有没有成功"**。）

### 0.6 所以那个 `while` 到底在干嘛

```cpp
while (in.read(chunk, sizeof(chunk))) {
  ...
}
```

假设文件 19 字节，块大小 8：

| 轮次 | 读前位置 | 这次读到 | 读后位置 | 条件结果 |
|---|---|---|---|---|
| 1 | 0 | 8 字节 | 8 | **真**（读满了） |
| 2 | 8 | 8 字节 | 16 | **真**（读满了） |
| 3 | 16 | 3 字节 | 19 | **假** ← 注意这里 |
| 4 | 19 | 0 字节 | 19 | 假 |

**第 3 轮为什么会假？** 因为你要 8 个，只给了 3 个 —— 操作「没完全成功」，置 `failbit`，转成 `false`。

**结果就是：最后那 3 个字节读到了缓冲区里，但 body 没执行，被无声丢掉。**

这就是为什么必须补一句：

```cpp
while (in.read(chunk, sizeof(chunk)) || in.gcount() > 0) {
  all.append(chunk, static_cast<size_t>(in.gcount()));
}
```

`gcount()` = 上一次 `read` 实际读到了几个字节。第 3 轮回合里它是 3，所以 `|| 3 > 0` 成立，body 得以再跑一次，把那 3 个字节收进去。第 4 轮 `gcount()` 是 0，两个条件都假，正常退出。

> **这不是"读同一个东西"，是"位置一直在前进，每次读到的都是新的，直到没有了"。**

## 1. 先建立心智模型：流

C++ 没有「文件」这个一等公民。它只有**流（stream）**。

流是一条**单向的字节管道**。你在这一头放东西，另一头出去。

| 你熟悉的 | 出口接哪 |
|---|---|
| `std::cout` | 屏幕 |
| `std::cerr` | 屏幕（错误通道，不缓冲） |
| `std::cin` | 键盘 |
| **`std::ofstream`** | **一个文件（只写）** |
| **`std::ifstream`** | **一个文件（只读）** |
| **`std::fstream`** | **一个文件（可读可写）** |

名字拆开就懂了：

```
ofstream  =  o  +  f  +  stream
              │    │     └── 流
              │    └── file，文件
              └── output，输出（你 → 文件）

ifstream  =  i  +  f  +  stream    （input，文件 → 你）
fstream   =  f  +  stream          （两个方向都有）
```

**所以你写的那一行，本质就是「造一个出口接着 wal.log 的 cout」。** 后面所有操作（`write`、`close`）都是作用在这个流对象上的，跟文件本身体没关系。

头文件：`#include <fstream>`（不是 `<iostream>`）。

## 2. 打开文件的两种写法

### 写法 A：构造时打开（你用的这个）

```cpp
std::ofstream out(kLogPath, std::ios::app | std::ios::binary);
```

`out` 这个对象**一诞生就带着一个已经打开的文件**。这就是为什么你找不到 `open` 这个词 —— 构造函数替你干了。

### 写法 B：先造对象，再 open

```cpp
std::ofstream out;                                   // 造了个"空流"，没连任何文件
out.open(kLogPath, std::ios::app | std::ios::binary); // 现在连上了
```

**两种完全等价。** 区别只有一个：写法 B 让你能在两件事之间插别的代码。

⚠️ **`out` 和 `std::ios::out` 是两回事。** 前者是你起的变量名，后者是「输出模式」。名字撞了纯属巧合，别被绕晕。

## 3. 打开模式：六个开关

模式本质是**一堆二进制位**，`|` 把需要的位同时拨上去。

| 模式 | 全名 | 作用 | 默认带不带 |
|---|---|---|---|
| `std::ios::in` | input | 允许读 | `ifstream` 默认带 |
| `std::ios::out` | output | 允许写 | `ofstream` 默认带 |
| `std::ios::trunc` | truncate | **打开就把文件清空** | `ofstream` 默认带 |
| `std::ios::app` | append | 每次写都跑到末尾 | 不带 |
| `std::ios::ate` | at end | 打开后把位置移到末尾（**但之后还能往回走**） | 不带 |
| `std::ios::binary` | binary | 二进制模式，不做任何字符翻译 | 不带（**Windows 上必须手动加**） |

### 3.1 `ofstream` 的默认模式是个陷阱

```cpp
std::ofstream out("wal.log");   // 等价于 out("wal.log", ios::out | ios::trunc)
```

**它会静默清空文件。** 不报错、不警告、文件变成 0 字节。

这就是为什么你必须写 `app` —— 不是"加上更好"，是**不加就毁数据**。

### 3.2 `app` 和 `ate` 的区别（最容易混的一对）

两个都是"末尾"，但**末尾的时机不同**：

| | 什么时候定位到末尾 | 之后能不能往回写 |
|---|---|---|
| `app` | **每一次写之前**，都强制跑到末尾 | 不能。`seekp` 到前面也没用，写还是落在末尾 |
| `ate` | **只在打开的那一瞬间** | **能**。之后 `seekp(0)` 就能从头覆盖 |

**你要的是 `app`。** 因为「只追加」这个语义必须被文件系统强制执行 —— 哪怕代码写错了想回退去覆盖，`app` 也不允许。这正是 LSM/WAL 需要的保证。

`ate` 是给「读文件大小」这种场景用的 —— 你代码里 `FileSize()` 用 `ios::ate` 就是这个原因：打开即到末尾，`tellg()` 就是文件长度。

### 3.3 常见组合

```cpp
std::ios::app | std::ios::binary          // 追加写，二进制 —— WAL 用这个
std::ios::in  | std::ios::binary          // 只读，二进制 —— 回放日志用这个
std::ios::in  | std::ios::out | std::ios::binary   // 读写同一个文件，不清空
std::ios::in  | std::ios::out | std::ios::trunc    // 读写，但先清空
```

## 4. 写：两组 API，别混用

### 4.1 格式化输出 `<<`

```cpp
out << "hello" << 42 << 3.14 << '\n';
```

**这是"给人看"的通道。** 它会把数字转成十进制文本、按本地格式排版。`42` 变成两个字符 `'4'` `'2'`。

你**绝对不能**用它写二进制数据。原因不只是"会排版"，还有下面 4.3 的截断问题。

### 4.2 非格式化输出 `write()`

```cpp
out.write(地址, 字节数);
```

**这是"给机器看"的通道。** 原样搬运，一个 bit 都不改。

它的签名和 `memcpy` 几乎一样：

```cpp
memcpy(目的地, 源地址, 字节数);      // 目的地写在参数里
out.write( 源地址, 字节数);          // 目的地固定是这个文件
```

### 4.3 为什么 `out << bytes.data()` 会静默丢数据

```cpp
std::string bytes = Encode(record);   // 19 字节，第 0 字节是 0x01，第 1 字节是 0x04，第 2 字节是 0x00

out << bytes;          // ✅ 写全部 19 字节。因为 std::string 的重载知道自己的长度
out << bytes.data();   // ❌ 只写 2 字节。因为 char* 被当成 C 字符串，遇到 0x00 就停
```

**`<<` 对 `const char*` 的处理方式是 `strlen` 式的** —— 它不知道长度，只能一个字节一个字节地找你 `'\0'`。你的记录第 2 个字节就是 `0x00`，所以它写完就收工，剩下 17 个字节**无声无息地消失**。

这就是为什么二进制一律用 `write()`：**它只认你给的字节数，不猜。**

顺带解释你的 `static_cast<std::streamsize>`：
- `write` 的第二个参数类型是 `std::streamsize`（**有符号**）
- `size()` 返回 `size_t`（**无符号**）
- 无符号转有符号，编译器要求你显式说明 —— 跟你 `static_cast<uint32_t>(key.size())` 是同一个道理

### 4.4 其他写接口（知道有就行）

| 接口 | 用途 |
|---|---|
| `out.put(c)` | 写**一个**字符 |
| `out.write(p, n)` | 写 n 个字节 ← **你用的** |
| `out.flush()` | 把缓冲区推给操作系统（不关文件） |
| `out.close()` | flush + 关闭 |

## 5. 读：明天 `Load()` 要用的

### 5.1 `read()` 和 `gcount()`

```cpp
char buf[1024];
in.read(buf, sizeof(buf));
std::streamsize n = in.gcount();   // 这次实际读到了几个字节
```

**注意 `gcount()`。** `read` 请求 1024 字节，但文件可能只剩 13 字节 —— 它不会失败，它会读 13 个然后停下。`gcount()` 告诉你到底读了几个。**不查 `gcount` 是读文件最经典的 bug。**

### 5.2 怎么判断"读到结尾了"

```cpp
std::string all;
char chunk[4096];
while (in.read(chunk, sizeof(chunk)) || in.gcount() > 0) {
  all.append(chunk, static_cast<size_t>(in.gcount()));
}
```

为什么不能只写 `while (in.read(...))`？因为**最后一次读如果只读到一部分，`read` 会置 `failbit`（不是只有 `eofbit`）**，循环条件为假，**最后那一截就丢了**。所以必须补 `|| in.gcount() > 0`。

> 这一条正好是你明天会撞上的东西。先记着，别到时候以为文件坏了。

### 5.3 四个状态位（`if (!f)` 不等于"到结尾了"）

| 状态 | 含义 |
|---|---|
| `good()` | 一切正常 |
| `eof()` | 读到物理结尾 |
| `fail()` | 一次操作失败（格式错、读不够、或已 eof） |
| `bad()` | 更严重：流本身坏了（磁盘错误） |

`if (!f)` 等价于 `if (f.fail())`。**`fail` 为真不代表"到结尾了"** —— 可能是一个字节都没读到。要区分，就得看 `eof()` 和 `gcount()`。

## 6. 二进制模式：Windows 上必须要的那一个词

C 语言诞生在 Unix，那里 `\n` 就是 `0x0A`，一个字节。
Windows 沿用了更早的电传打字机传统：换行是 `\r\n` 两个字节。

所以 CRT 在**文本模式**下自作主张做翻译：

| 操作 | 文本模式的行为 |
|---|---|
| 写 `0x0A` | 变成 `0x0D 0x0A` 写出去 |
| 读 `0x0D 0x0A` | 变回 `0x0A` 给你 |

**对文本文件这是好事**（记事本能正常显示换行）。**对你的 WAL 是灾难**：

```
Encode 出来            19 字节，其中某处是 0x0A
文本模式写进去          20 字节（0x0A 变 0x0D 0x0A）
Load 时按 19 字节读     读到的是错位的数据，后面的全乱
```

而 `binary` 模式关掉所有翻译：**字节进，字节出，一个 bit 都不动。**

> 另外还有个老包袱：老的 MSVC CRT 在文本模式读时会把 `0x1A`（Ctrl+Z）当成文件结束符。现代 UCRT 是否仍如此我没实测过，但**结论完全不受影响**：二进制数据，永远加 `binary`。

## 7. 缓冲：`write` 之后数据其实还没到磁盘

这是今天最重要的一个认知，也是整个 WAL / 崩溃恢复的起点。

```
你的程序               操作系统                硬盘
┌──────────┐  write()  ┌──────────┐  close()  ┌──────────┐
│ std::string│ ───────▶│ 用户态缓冲 │ ────────▶│  wal.log │
│  (你的内存)│          │  (几 KB)  │  或flush  │  (磁盘)  │
└──────────┘          └──────────┘           └──────────┘
      └────────────────────────┘
        进程崩溃 → 这一段全部消失
```

`out.write(...)` 之后，字节**只是在 ofstream 内部的一个缓冲区里**。它在你的进程内存里，硬盘上什么都没有。

三种情况会把它推出去：
1. 缓冲区满了（几 KB）
2. 你调用 `flush()` 或 `close()`
3. 对象析构（会自动 close）

**所以：`write` 成功 ≠ 数据安全。** 你今晚跑了两次程序，数据还在，是因为第一次的 `close()` 生效了。如果第一次跑到一半被 `kill`，那 32 字节一个都不会有。

> 而且 `close()` 也只保证"交给了操作系统"，操作系统还有自己的页缓存 —— 真要保证落到盘片的磁道上，得 `fsync()`。
> **这就是 10-26 要做的第一件事**，也是 WAL 存在的全部理由。

## 8. 相对路径：相对于"当前工作目录"，不是 exe 的位置

```cpp
std::ofstream out("wal.log", ...);
```

它在哪创建？**取决于你从哪个目录运行程序**，不是 exe 放在哪。

```
cd D:\code\lsm-kv
.\build_win\demo_file.exe          →  D:\code\lsm-kv\wal.log

cd D:\code\lsm-kv\build_win
.\demo_file.exe                    →  D:\code\lsm-kv\build_win\wal.log
```

**同一个 exe，两个不同的文件。** 这是新手最常见的"我明明写了，怎么找不到文件"。

排查：程序里 `printf` 一下当前目录，或者干脆用绝对路径。

## 10. 自测题

1. `std::ofstream out("a.log");` 这行会不会清空 `a.log`？为什么？
2. `app` 和 `ate` 都能"到末尾"，你写 WAL 为什么必须用 `app`？
3. `out << bytes.data()` 和 `out.write(bytes.data(), bytes.size())` 写同一个 19 字节的记录，分别写出多少字节？
4. `read(buf, 1024)` 在文件只剩 13 字节时返回什么？你怎么知道读了 13 个？
5. 为什么 `while (in.read(...))` 会丢掉最后一截数据？
6. 调用完 `out.write(...)` 之后立刻拔电源，数据还在吗？

<details>
<summary>答案</summary>

1. **会。** `ofstream` 默认模式含 `trunc`，打开即清空。
2. `app` 强制**每一次写**都定位到末尾，且在文件系统层面禁止往回覆盖 —— 这是"只追加"必须的硬保证。`ate` 只在打开瞬间定位，之后可以 `seekp` 回去覆盖，保不住这个语义。
3. `<<` 写 **2 字节**（第 2 个字节是 `0x00`，被当成字符串结尾）；`write` 写 **19 字节**。
4. 返回流对象本身（可以链式判断），但**只读到 13 个字节并置 `failbit`**。用 `gcount()` 取 13。
5. 因为最后一次读不满会置 `failbit`，条件变假直接退出循环，那一截没被 append 进去。要补 `|| in.gcount() > 0`。
6. **不在。**（大概率）数据还在进程的缓冲区里，没到磁盘。除非缓冲区正好满了被自动刷出去。

</details>

## 11. 一句话总结

| 概念 | 一句话 |
|---|---|
| `ofstream` | 出口接文件的 cout |
| 声明即打开 | 构造函数就是 `open`，所以看不到 `open` 这个词 |
| 默认模式 | `ofstream` = `out + trunc` → **打开就清空** |
| `app` vs `ate` | `app` 每次写都回末尾且禁止覆盖；`ate` 只在打开时到末尾 |
| `<<` vs `write` | `<<` 是文字给人看，`write` 是字节给机器读。二进制只用 `write` |
| `binary` | Windows 上不加，`0x0A` 会被膨胀成 `0x0D 0x0A` |
| 缓冲 | `write` 只写到内存缓冲区；`close` 才交给操作系统；`fsync` 才到盘 |
| 相对路径 | 相对于**当前工作目录**，不是 exe 所在目录 |
