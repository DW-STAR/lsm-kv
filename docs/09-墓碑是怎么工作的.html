墓碑是怎么工作的

LSM 的删除不是把数据拿掉，是给这个 key 追加一份死亡通知。

01先看一个具体的麻烦

下面四步是真实的时序。注意第三步：Delete 执行的那一刻，MemTable 里根本没有 b。

MemTable（内存，跳表）—
SSTable L0（磁盘，只读）—

02于是 Delete 只有一条路

「查一下，不在就跳过」是 std::map::erase 的直觉，在 LSM 里是致命错误。点两个标签对比。

03墓碑就是一条普通记录

它躺在跳表的节点里，字段和别的记录一模一样，只有 type 不同。

key
"b"
value
""
type
kDelete
next[0..k]
指针

因为结构完全一样，写入路径一行都不用新写： Delete(k) 就是 Insert(k, "", kDelete)。 查找前驱、同 key 覆盖、随机层数、升层补哨兵、++size_ —— 全都复用。

删除是写入的一种。LevelDB / RocksDB 的 Delete 走的就是 Put 完全相同的代码路径。 记住这句，后面的 compaction、MVCC、事务都会顺很多。

04Get 得跟着改

墓碑在链表里，查找一定能碰到它。不处理的话，用户会看到「b 还在，值是空串」。

找到什么Get 应该返回为什么
type == kPut true + 写出参 正常命中
type == kDelete false，出参不动 对读者而言这个 key 已经不存在了
什么都没找到 false 从来就没有这个 key

位置很关键：return false 必须写在 *value = ... 之前。 写在后面，出参已经被墓碑的空串写脏了 —— 返回值虽然是 false， 但调用方如果先用了出参，就会拿到错值。

为什么不把这次判断推给调用方？因为那是 bug 工厂 —— 总有人忘。 层次越低的封装，越该把「用户视角的正确语义」做掉。 LevelDB 的 MemTable::Get 就是在这里把 kTypeDeletion 转成 NotFound。

05两层视角必须分开

同一份内存，两个读者，看的东西不一样。混淆这两层，Week 5 落盘时必炸。

视角看到什么谁在用
物理层
DebugFind		 每个 key 一条记录，包含墓碑。Size() 也算它们。 compaction、落盘遍历、测试
逻辑层
Get / Delete		 墓碑 = 不存在。用户永远看不见 kDelete。 上层 DB、业务代码

Week 5 的坑就藏在这里：MemTable 落盘时不能跳过墓碑。 如果遍历时把墓碑过滤掉，磁盘上那份老数据就永远删不掉了。 墓碑必须写进 SSTable，一路沉到最底层，由 compaction 在那里才真正消灭。

B-Tree 的删除是「就地消灭」；LSM 的删除是「追加一个噩耗」。
前者需要先找到东西，后者不需要 —— 因为它不知道东西在哪一层。
