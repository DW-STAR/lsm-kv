## 教学约定（新会话必须先读这段）

1. **规格给全，实现不给** —— 只给布局图、积木清单、验收标准，代码他自己写。
2. **卡 40 分钟是必要的** —— 不要因为他问得早就提前给答案。
3. **提问三句话格式** —— 想做什么 / 现在什么现象 / 你猜是什么原因。
4. **允许写得丑** —— 先写对，再写好。
5. **⭐ 每个新概念先讲底层模型，再上语法**（2026-10-22 他主动提出的）
   > 原话：「你似乎忘了我是个初学者，很多语法特性或一些计算机知识都没提前解释，我需要理解底层概念。」

   执行细则：
   - 凡是涉及**操作系统概念** —— 文件、句柄、缓冲区、位置、进程 vs 内核、副作用、系统调用 —— **必须先讲清"这是什么"，再给 API**。
   - **不要假设他懂**：`<fstream>`、文件句柄、`gcount()`、`failbit`、副作用、隐式 bool 转换。
   - 判断标准：**一行代码里出现两个以上他没见过的名词，就先停下来解释名词，别往后走。**
   - 有一个很好用的讲法：**把新东西接到他已经懂的东西上**。例：文件流的"位置" = 他 `Decode` 里的 `p`，区别只是"谁负责挪"。这类类比命中率最高。
6. **⭐⭐ 每个模块必须能回答「为什么」，否则算作废**（2026-10-23 他主动提出的）

   > 原话：「涉及底层一点就是要懂什么这样做，防止出现这种作废的情况。但大多数人会把它做废，废法有三种：只跟着教程抄一遍能跑通、只顾代码量、没有对比数据。这三种的共同点是：你只能回答『我做了什么』，答不出『我为什么这么做』。」

   **三种废法（对号入座，每周自查一次）**：

   | 废法 | 表现 | 症状 |
   |---|---|---|
   | ① 抄一遍能跑通 | 照教程/照我给的骨架填完，跑出 PASS | 删掉代码重写就写不出来 |
   | ② 只顾代码量 | 追求"今天写了 200 行" | 说不出哪一行是必须的 |
   | ③ 没有对比数据 | 说"性能变好了"，但给不出数字 | 面试官一问"快多少"，哑住 |

   **验收三问 —— 每个模块做完，必须不看代码答出来**：
   1. **为什么需要它？** 没有它，程序会出什么具体的错？
   2. **为什么这样做，而不是另一种？** 另一种做法的代价是什么？
   3. **怎么证明它对了？** 要能给出数字、对比，或者一个「故意弄坏」的失败案例。

   **执行细则（我的责任，不只是他的）**：
   - 我布置任务时，**必须先把「为什么需要它」讲清楚，再给规格**。不给 why 直接给 TODO，就是逼他走废法 ①。
   - 每个模块的验收里**至少要有一个可比数字**（字节数 / 条数 / 次数 / 时间），禁止只写"跑通了"。
   - 他做完后，我要**至少问一次第 2 问**（为什么不是另一种做法）——这是三种废法里最容易被漏掉的。
7. **⭐⭐ 讲概念的顺序固定为：术语 → 定义 → 代码 → 比喻**（2026-11-03 他第三次提出的同类问题，这次直接定为硬规则）

   > 原话：「一句话：有序链表 + 抛硬币决定的多层索引。 啥叫抛硬币 你每次讲的东西有点特殊指代我就看不懂了」
   > 「以后先用专业一点的说法再给出比喻」

   **病根**：我习惯先抛一个比喻当抓手，再补定义。对他来说，**比喻本身就是一个新黑箱**——「抛硬币」不是他能执行的任何动作，他既不知道硬币是什么，也不知道在哪一行抛。

   **硬规则（四步，不许调序，不许跳步）**：
   1. **术语**：先说出这个机制的正式名字（例：*几何分布随机层数*）。
   2. **定义**：一句话说清它到底在算什么（例：*每升一层的概率固定为 1/2，层数 L 满足 P(L=k)=2^-k*）。
   3. **代码**：给出**唯一对应**的那一行/那几行（例：`if ((NextRandom() & 1) == 0) ++level; else break;`）。这一步不能省——没有代码的比喻等于没讲。
   4. **比喻**：最后才允许出现（例：*等价于反复掷一枚硬币，正面就升一层，反面就停*）。

   **判定标准**：任何一个比喻，如果我在同一段里没有把它落到具体代码行或具体动作上，这段讲解算不合格，要重写。

### 手敲版（面试/换机器时要会，别丢）

**2026-10-24 踩过**：我给的是 bash 写法（`&&` + `./`），他粘贴进 PowerShell 直接报
「标记"&&"不是此版本中的有效语句分隔符」。**以后所有命令一律用这个格式给。**

PowerShell 5.1 的正确写法 —— 用 `;` 加 `if ($?)`：

```powershell
g++ -std=c++17 -Iinclude src/demo_log.cpp -o build_win/demo_log.exe; if ($?) { .\build_win\demo_log.exe }
```

`$?` = 上一条命令成功了没有。这样**编译失败就不会运行**，避免"跑的是旧 exe"。

四个 demo 的命令：

```powershell
g++ -std=c++17 -Iinclude src/demo_record.cpp -o build_win/demo_record.exe; if ($?) { .\build_win\demo_record.exe }
g++ -std=c++17 -Iinclude src/demo_file.cpp   -o build_win/demo_file.exe;   if ($?) { .\build_win\demo_file.exe }
g++ -std=c++17 -Iinclude src/demo_load.cpp   -o build_win/demo_load.exe;   if ($?) { .\build_win\demo_load.exe }
g++ -std=c++17 -Iinclude src/demo_log.cpp    -o build_win/demo_log.exe;    if ($?) { .\build_win\demo_log.exe }
g++ -std=c++17 -Iinclude src/demo_wal.cpp    -o build_win/demo_wal.exe;    if ($?) { .\build_win\demo_wal.exe }
g++ -std=c++17 -O2 -Iinclude src/demo_crc32.cpp -o build_win/demo_crc32.exe; if ($?) { .\build_win\demo_crc32.exe }
g++ -std=c++17 -Iinclude src/demo_corrupt.cpp -o build_win/demo_corrupt.exe; if ($?) { .\build_win\demo_corrupt.exe }
g++ -std=c++17 -Iinclude src/demo_crash.cpp  -o build_win/demo_crash.exe;  if ($?) { .\build_win\demo_crash.exe dirty }
```

**铁律：`; if ($?) { }` 不能省。** 编译失败时旧的 `.exe` 还在，跑它会给出一个"看起来对"的假结果 —— 10-24 就被这个骗过一次。

## 技术栈：C++ 主，Go 辅（双修）

| | 角色 | 说什么 | 什么时候补 |
|---|---|---|---|

- **顺序不能颠倒。** 现在同时开两条战线，考研先崩。C++ 这条线已经跑了半个月，沉没成本正在变成资产，别停下来。

### ✅ 10-31 完成：`Decode` 返回 `Status`，`Load` 分清「尾部残片」和「中间损坏」

他的原话：**「按道理来说 decode 也可以判断 我也不知道 你直接改吧」** ——

**他的直觉哪里对、哪里不成立**（已讲）：

- 对的部分：`Decode` 确实判断得了「我读到的位置越过了缓冲区末尾」。
- 不成立的部分：它**判断不了这个末尾是不是文件的末尾**。它只拿到一段 `const std::string&`，
  同一段字节可能是整个文件，也可能是文件的前 200 字节。

**接口变更**（`record.h`）：

```cpp
-inline bool Decode(const std::string& buf, size_t offset, Record* out, size_t* consumed);
+inline Status Decode(const std::string& buf, size_t offset, Record* out,
+                     size_t* consumed, size_t* short_by = nullptr);
```

`short_by` 只在「字节不够」时填（还差多少字节）；CRC 失败时保持 0。
**`short_by > 0` → 可能是正常残片；`short_by == 0` → 一定是内容损坏。**
默认参数 `= nullptr` 让老调用点不用改签名 —— 这是为了不再犯「静默改用户代码」那次的错。

**新增 `kMaxRecordSize = 64 MiB`**（`record.h`）：长度字段被改成离谱值时直接判损坏，
不再伪装成「尾部截断」。这把盲区从「任意大数」压到「落在 [剩余字节, 64 MiB] 之间」。

**`Load` 新逻辑**（`append_only_log.h`）：

| 现象 | 判据 | 处理 |
|---|---|---|
| 字段读不全 | `short_by > 0` | 尾部截断 → **返回 OK**，记 `truncated_bytes_` |
| 读全了但 CRC 不对 | `short_by == 0` | **返回 `Corruption`**，拒绝继续 |

- 截断返回 OK，因为**崩溃恢复是 WAL 的日常，不是异常**；那半条记录从未被承诺过。
- 但**正常路径不等于无声无息** —— `truncated_bytes()` 把「丢了多少」报出来。
- 截断时**不去改文件**：恢复路径上的任何写操作，都可能让你从「崩过一次」变成「崩过两次」。

### ✅ 11-01 完成：`flush` / `fsync` 分家 + 真的崩溃现场

**新工具 `src/demo_crash.cpp`** —— 上周的 `demo_corrupt` 是拿字符串 `resize` 伪造残片，
今天是让进程**真的死在写操作中间**。

核心手法：`std::_Exit(0)`。
- `return 0` / `exit(0)` → 跑析构 → `ofstream` 析构时 flush → 数据出去
- `std::_Exit(0)` → **立刻死**，不跑析构、不 flush、不跑 atexit —— 就是 `kill -9` 的样子

七个模式：`dirty` / `clean` / `size` / `bulk N CRASH_AT` / `halflast N K` / `verify`。

**四个实测数字（这是今晚最硬的证据）：**

| 场景 | 命令 | 结果 |
|---|---|---|
| 写 23 字节，**不 flush**，立刻 `_Exit` | `dirty` | 文件 **0 字节** |
| 写 23 字节，**flush 后** `_Exit` | `clean` | 文件 **23 字节** |
| 写 1000 条，写到第 347 条前 `_Exit` | `bulk 1000 347` | `OK` / **347 条** / 8675 字节 / 前缀全对 |
| 写 500 条完整，第 500 条**只写一半** | `halflast 1000 500` | `OK` / **500 条** / `truncated 12` / 前缀全对 |

**必须能答（也是他 11-01 的验收题）：**

1. **`kill -9` 到底丢不丢数据？→ 不丢。**
   它杀的是**进程**，杀不掉**内核**。数据 flush 之后在内核页缓存里，
   那是操作系统的资源，进程死了照样会被写进磁盘。
2. **那 `fsync` 防的是什么？→ 断电 / 蓝屏 / 内核 panic。**
   那时候内核也没了，页缓存里的脏页跟着没。
   **`flush` 和 `fsync` 的分工就是「怕进程死」和「怕机器死」。**
3. **掉电丢数据丢在哪一层？→ 内核页缓存**（flush 成功之后、fsync 之前的那一段）。

**性能账（今天实测）**：347 条 / 6.482 ms ≈ **19 μs/条**（含 flush）。
若每条 fsync：机械盘 5~10 ms → 1000 条要 **5~10 秒**，比现在慢 **300~500 倍**。
所以工业级用 **group commit**（一批请求共用一次 fsync，10 个请求等 1 次 5 ms = 每个 0.5 ms）。
LevelDB 的 `WriteOptions::sync` 默认就是 `false` —— 连 fsync 都不做，靠 OS 定期刷盘兜底；
Redis AOF 的 `everysec` 是 1 秒刷一次。**这是性能 vs 断电后可能丢多少数据 的真实取舍点。**

### ✅ 11-06：Delete（墓碑）—— 完成

**他一次交对，`ALL CHECKS PASSED`。** 但过程中冒出一个真问题，比 Delete 本身值钱。

**今晚的核心不是代码，是两个语义问题。**

`Delete` 本体只有一行：`return Insert(key, "", RecordType::kDelete);`。
写出来 10 秒。但下面的判断错了，代码再对也没用。

**① 不许先查再删（坑 1）**

`std::map::erase` 找不到就什么都不做。LSM 不能这么干：

```
昨天  Put("b","2")  → MemTable 满了，落盘成 SSTable
今天  Delete("b")   → MemTable 里根本没有 "b"
```

「查一下，不在就跳过」→ 磁盘上那份 `b` 永远活着，删了等于没删，还没有任何报错。

**LSM 的删除必须无条件写墓碑**：它不知道老数据在哪一层，只知道「从此刻起 b 是死的」。
清理交给 compaction —— 它合并时看到墓碑，才会把更老的那份一起扔掉。

> **B-Tree 的删除是「就地消灭」，LSM 的删除是「追加一个噩耗」。**
> 这是两种存储引擎最根本的区别之一，也是今晚唯一值得背下来的一句。

**② `Get` 必须跟着改（这是今晚的第二个动作）**

加了墓碑之后，`Get("b")` 会命中一条 `type == kDelete` 的记录，
现有代码会高兴地返回 `true` 并把空 value 交给调用方 —— 用户看到「b 还在，值是空串」。

正确语义：**墓碑 = 不存在**。改法一句话，但位置关键：**必须在写 `*value` 之前返回**，
否则出参已经被墓碑写脏了。LevelDB 的 `MemTable::Get` 就是在这里把 `kTypeDeletion` 转成 `NotFound`。

**为什么不把这次判断推给调用方**：那是 bug 工厂，总有人忘。层次越低的封装，
越该把「用户视角的正确语义」做掉。

**③ `Size()` 会 +1，哪怕删的是从没存在过的 key**

墓碑也是真实记录，也占内存。MemTable 的「大小」按字节算，不按活着的 key 个数算。

**④ 返回值恒为 `true`**

别写成「找不到就返回 false」—— 那等于把坑 ① 写进了签名。
`true` = 「这条删除已被接受」，不是「确实删掉了一条」。

**架构上的分层（今晚真正建立的心智模型）**

| 层 | 看到什么 | 谁用 |
|---|---|---|
| 物理层（`DebugFind`） | 每个 key 一条记录，含墓碑 | compaction / 落盘遍历 |
| 逻辑层（`Get` / `Delete`） | 墓碑 = 不存在 | 用户 / 上层 DB |

两层必须分开，否则「磁盘遍历要跳过墓碑」这件事（Week 5 的真坑）会炸。

**新增的测试**

- `[12]` 改用 `DebugFind` —— **规格变了，测试必须跟着变**，否则测试在骗你
- `[13]` 墓碑 13 条：删不存在的 key 也写 / `Get` 查不到 / 节点没被摘 / 重复删幂等 / 删完再写能复活 / 不变量仍成立

**★ 今晚真正的收获不是 Delete，是他自己撞出来的一个问题**

原话：

> 「单纯的 bool 变量返回的 insert 逻辑有问题，完全无法很好的维护 size 这个变量。

他先写了 `if (ans) { size_--; }`，然后自己发现两种情况不一样，把注释掉了。

**他的诊断方向对了一半，另一半是把两个不同的问题混成一个。** 拆开：

**① `size_` 记的是物理记录数，不是活着的 key 数**

```
size_ = 活着的 key + 墓碑
```

`Insert` 里 `++size_` 挂在「建了新节点」这条路径上，所以：
- 删不存在的 key → 新墓碑 → **已经 +1**，正确
- 删存在的 key → 走覆盖分支 → **不变**，正确

再补一个 `size_--` → 两种情况全算错（第一种少算一条真实记录，第二种凭空减一条）。
**所以正确的做法不是"想办法减对"，是"一行都别碰"。**

他之所以觉得必须减，是因为心里的 `size_` = 活 key 数。这个定义在 B-Tree 世界成立，
在 LSM 里不成立：MemTable 关心的是**内存占用**，决定何时冻结落盘的是字节数不是 key 个数，
墓碑也占内存，就该算进去。（LevelDB 按字节估算，我们先用记录数凑合，Week 5 换。）

**② 「bool 丢了信息」—— 丢的是原因，不是新旧**

| 觉得缺的信息 | 该不该补 |
|---|---|
| 这次是**新建**还是**覆盖** | **不该知道**。LSM 写入是幂等追加，新/旧对上层无意义；数据一旦分层落盘这信息彻底失效。要它 = 让调用方依赖一个迟早不成立的实现细节 |
| 失败**为什么**失败 | **该知道，但现在用不上**。内存结构只有 `bad_alloc`（抛异常），`bool` 恒 true 是对的 |

他直觉里「bool 不够用」是对的，但把「缺原因」误诊成「缺新旧」。
`Status` 不是用来回传新旧的，是用来回传原因的 —— 而原因要等 Week 5 有 IO 才出现。

**给 Status 的判据（已写进 `skip_list.h` 注释，以后可复用）**：
- 失败只有一种可能，或失败可直接抛异常 → `bool`
- 失败有多种原因、且调用方要**分开处理**（重试 / 降级 / 报错）→ `Status`

`include/lsmkv/status.h` 第一天就建好了，一直没有真正的用武之地 —— 它的场子在落盘。

**为什么这个问题值得早起半小时想**：他第一次触到「同一个变量，物理语义和逻辑语义不同」。
这跟今晚讲的「物理层 / 逻辑层」是同一件事的两面。Delete 只是把它挤出来了。

| | 职责 | 什么时候 |
|---|---|---|
| ① | **记账**：我占了多少内存？该不该冻结？ | 今晚 |
| ② | **状态**：冻结后只能读不能写（immutable） | 11-09 |

单独替换了。**封装不是为了藏起来，是为了让两边都能只干一件事。**

**今晚真正要他想清楚的一处（记账的度量口径）**

同一个 key 写第二次，SkipList 覆盖、节点数不变。`bytes_` 该不该涨？

→ **继续涨。这是 LevelDB 的真实做法**：MemTable 的内存来自 arena，
写入只往后要新内存、**永不回收**，旧那条确实还占着，等整张表落盘才一起释放。

所以：

```
bytes_ = 这张表累计吃进去多少字节
       ≠ 现在还活着的数据有多少字节
```

**这和上周 `SkipList::size_` 是同一个坑的同一个解法** —— 两个计数器，
两次都是「语义错、算术对」。这是本周要反复钉的一课：
**问清楚一个计数器在数什么，比算对它更重要。**

**第二处：墓碑不免费（真实事故模式）**

如果 `Delete` 只按 `value.size()` 记账，会得到：删 100 万个 key，

`ShouldFlush()` 永远 false，最后 OOM。`demo_memtable` 的 `[3]` 专门验它，
提示语直接写 `you only counted value.size() -- tombstones would OOM you`。

同一件事，在两层里答案不同：

- `MemTable::Put` 必须返回 `Status` —— 11-12 接上 WAL 后，第一件事是写磁盘，**会**失败

**不是 bool 变差了，是这一层的失败原因变多了。** 这句话就是答案。

### ✅ 11-09（周一）：冻结（immutable memtable）

**今晚先算账，再写代码。** 代码只有 4 行（两个函数各加两行守卫），
剩下全部时间给一个测量——因为它决定了整个设计。

**问题**：MemTable 写满了，为什么不直接把内容倒进文件、然后清空继续写？

**答案在 `demo_flush_cost` 的实测里**（这台机器，4MB，41943 条 100 字节记录）：

| 写法 | 耗时 | 吞吐上限 |
|---|---|---|
| A 攒成 4MB 一次写 | ~2~10 ms | **977 万条/秒** |
| B 4 万次 fwrite（stdio 缓冲） | ~9 ms | — |
| C 4 万次 fwrite + 每条 flush | ~196 ms | — |
| D 4 万次 fwrite + 每条 fsync | **84 秒** | **501 条/秒** |

- `B vs C = 21x`（合并系统调用）
- `D vs B = 9152x`（每条都碰盘）
- **吞吐上限**：`501 条/秒` vs `977 万条/秒` → **相差 19534 倍**

一句话：**每条都落盘的话，你的 QPS 上限是 501。目标是 10 万，差 200 倍。**

还有第二笔账：同步刷一张 4MB 表要 **12.7 ms**，这期间写入线程**完全停摆**——
10 万 QPS 下积压 1270 个请求，尾延迟从微秒跳到十几毫秒（三个数量级）。

> **⚠️ 11-09 深夜修正（重要，别再讲错）**：上面这两笔账要分开记账，它们答的不是同一个问题。
>
> | 数字 | 管什么 | 换算 |
> |---|---|---|
> | D：498 条/秒 | **吞吐上限** | 一次 fsync = 2.006 ms → 1/0.002006 |
> | A：2~4 ms / 张 | **尾延迟** | 100k QPS 下 409 个请求排队 |
>
> 按吞吐算，即使**同步**刷盘也只占 1% 的时间占用：
> 4MB 表装 41943 条 → 100k QPS 下 0.42 秒满一张 → **2.4 张/秒** × 4.1ms = 9.8ms/秒。
> 也就是说**"刷得太慢"根本不成立**。冻结机制的头号理由不是性能，是正确性：
>
> 1. **不能在别人读的时候改这棵树** —— 后台线程正遍历建 SSTable，插一个节点就悬空/漏数据
> 2. **冻结 + 换表必须原子** —— 否则一条 Put 写进旧表，又被刷盘覆盖
> 3. **SSTable 必须一次成形** —— 文件内 key 有序，不能先写一半再补中间
>
> 性能（前台不等那 4.1ms）是**附带收益**，不是主因。这个区分以后再讲错了，
> 他会以为"只要刷得够快就不用冻结" —— 那是错的。


**所以真实做法是「换表」而不是「刷表」**：

```
写满了 → 当前表标成冻结（只读）
        → 开一张新空表，写请求立刻转向
        → 旧表交给后台线程慢慢刷，前台一秒不等
```

这就是 **immutable memtable**，LevelDB / RocksDB / TiKV 一字不差。

**今晚的代码（TODO 5）**

`Freeze()` / `IsFrozen()` / `CheckWritable()` 我写好了，他只需要在 `Put` 和 `Delete`
**最前面**各加两行，过同一个关口。

- 为什么必须是最前面：冻结后 `bytes_` 一字节都不能涨，表定格了尺寸还在长 = 自相矛盾
- 为什么返回 `InvalidArgument` 而不是 `IOError`：磁盘坏是**环境**问题，
  往冻结表里写是**调用方写错了**。混用枚举值，上层就做不出正确决策
- 为此给 `status.h` 补了 `kInvalidArgument`（LevelDB 里同名）

**为什么"冻结"必须真只读，不能靠约定**：后台线程正在遍历这张表，
这时来一条 Put 就改了遍历中的指针——漏数据或死循环。这不是风格问题，
是并发正确性的必要条件。

> 顺手闭环他 11-05 那个「我不会改链表，const 有什么意义」：

### 🔄 11-10（周二）：查找链（active → immutable）

**开场问题**：内存里现在有两张表，一张能写、一张只读。来一个 `Get("k")`，先查哪张？

他答：**先查能写的**，因为那张表里可能有更新的信息（墓碑、修改）。**对，理由也对。**

补的三层：

1. **「新赢」不是约定，是必须** —— 老表赢 = 时光倒流，昨晚的写会被一小时前的值盖掉
2. **墓碑和值完全平权** —— 新表里查到墓碑，立刻 not found，不许翻老表
3. **顺序是「从新到旧」，不是「能写的先查」** —— 冻结那张仍然比 SSTable 新

#### 今晚真正的技术骨头：`bool` 装不下三态

`SkipList::Get` 命中墓碑返回 `false`，和"没有这个 key"完全一样。
单表够用，**双表就废了** —— 因为 `false` 之后要做的事相反：

```
kNotFound → 继续查老表
kDeleted  → 立刻停手
```

同一个 `false`，两种后续。这就是 11-06 那句「bool 不够用」的第二次兑现，
只是这次逼出问题的不是"失败原因"，是"**命中的性质**"。

**解法（分层，不平铺）**：

| 层 | 函数 | 视角 |
|---|---|---|
| SkipList | `Find(key, value, type)` | 物理：找到就 true，墓碑也 true | 11-10 我写 |
| SkipList | `Get(key, value, type)` | 用户：墓碑 = 不存在（`Find` 之上） | 11-10 我写 |
| MemTable | `Lookup(key, value)` → `LookupResult` | 三态：kNotFound / kFound / kDeleted | **TODO 6，他写** |
| MemTableSet | `Get(key, value)` | 顺序 + 命中即终结 | **TODO 7，他写** |

`enum class LookupResult` 放在 `mem_table.h` 命名空间级 —— SSTable 那边以后直接用同一套。

**谁负责让这块字节活着**，不是"快 vs 慢"，也不是"字符串 vs 字节数组"。

为什么前四周没见过它：
- 他写的三个结构（SkipList / MemTable / MemTableSet）都是**存储结构**，必须**拥有**数据
  → 只能是 `std::string`。往节点里塞 Slice，调用方的临时对象一析构节点就野了。
- Slice 从 10-16 就在 `db.h` 里了，只是那之后他一直待在实现层，没机会碰到它。

`demo_slice`（新增）实测：

| 2,000,000 次传参 | std::string | Slice | 倍数 |
|---|---|---|---|
| 短 key 8B（SSO） | 146 ms | 19 ms | **7.3x** |
| 长 key 64B（堆） | 397 ms | 22 ms | **17.9x** |

- 每次传参：std::string **73 ns**，Slice **9 ns**
- 折到 10 万 QPS：每 10 万次请求省 **6338 µs ≈ 0.6% CPU**

**0.6% 救不了 QPS** —— 所以别拿性能当 Slice 的存在理由。它真正的价值是
**让"我只是借一下"成为接口上能写出来的东西**，于是复制只发生在唯一该处（`ToString`）。

`[3]` 还演示了它为什么必须带长度：`"a\0b"` 走 c-string 只剩 1 字节，走 `Slice(std::string)` 是 3 字节
—— `test_basic` 第 6 条的二进制安全就赌这个。

`[4]` 演示代价：返回一个指向局部变量的 Slice，`size()` 还是对的（67），
但内存已经没了。**这是 Slice 唯一的、也是致命的坑。**

**一句话规则**：`Slice` 只活在调用的那一瞬间，活过这个函数的东西必须是 `std::string`。
这道边界以后还会出现三次：写 WAL、写 SSTable、读 SSTable（mmap 页上直接切 Slice）。

#### 文件格式 v1（今晚版，没有索引）

```
[record 0][record 1]...[record N-1]     ← data 区，key 严格递增
[data_end 8B][count 8B][magic 8B]       ← footer，固定 24 字节
```

- 每条 record 用的就是 `record.h` 的 `[CRC 4B][type 1B][klen 4B][key][vlen 4B][value]`
- **footer 必须定长、必须放最后**：打开时只知道"文件多长"，从末尾往回退 24 字节
  是唯一不依赖任何前置信息的定位方式。footer 一变长，就得先读头才知道 footer 在哪，
  而头的位置又要先读 footer —— 死循环。（`record.h` 把 CRC 放最前面是同一个思路的镜像。）
- `magic = "LSMSST01"`：挡住"把 `wal.log` 或一张图片当成 SSTable 打开"这种情况。
  没有它，那种误用会表现成一堆莫名其妙的 Corruption。

#### 三个今晚要立住的道理

**① 有序是 SSTable 存在的理由，而且必须自己守住**

MemTable 用的是 SkipList，倒出来**天然有序**，一分额外力气都不花。而这份"顺手的秩序"
是后面所有性能的来源：二分索引、compaction 归并、同一个 key 的新旧版本必然相邻。

但**格式本身不保证有序**。`Add` 里不检查的话：文件照样写得成功、读得回来、测试全绿 ——
唯一的症状是"某些 key 查不到"，而且只在大数据量下出现。一旦无序，后面所有依赖有序的
东西（二分、归并）都会给出**错误答案而不是报错**。

所以 `Add` 第二步就是：

```cpp
if (count_ > 0 && record.key <= last_key_)
  return Status::InvalidArgument("sstable: key order violated: " + record.key);
```

用 `<=` 不用 `<`：同一个 key 出现两次就是上游有 bug（MemTable 里一个 key 只有一条），
必须挡住，不能"随便留一个"。

**② 半成品文件不能长得像好文件**

`SSTableBuilder` 没 `Finish` 就析构 → 不补 footer → 打开时必然报 Corruption。这是**故意的**：
一个"看起来完整、其实少了几条"的表，比一个明确读不开的表危险一百倍。
要么整份交出去，要么明确作废，没有中间状态。`demo` 的 `[7]` 验这一条。

**③ `file_` 关完必须立刻置 nullptr**

不置空的话，后续误调 `Add` 会往一个已关闭的 `FILE*` 上写 = 未定义行为，
可能崩、也可能"成功"写进一块已经不属于你的缓冲区。
**悬空指针的定义就是这样来的：指针还在，指向的东西已经没了。** 置空是最便宜的保险。

#### 刻意留的缺口：没有索引

`SSTable::Open` 把**整个文件读进内存**，`Get` 在整块内存上**线性扫**。
真实引擎里完全不可接受（一个 SSTable 可能几百 MB；每查一条扫全文件）。

今晚先这么写，因为要验证的是**字节格式**，不是性能 ——
**先把数据搬对，再谈怎么少搬。** 顺序反了会同时抓两只兔子。

`demo` 的 `[6]` 把这笔代价实测出来了：

| 条数 | 文件 | 200 次查询 | 单次 |
|---|---|---|---|
| 5,000 | 170 KB | 342 ms | 1.7 ms |
| 40,000 | 1.4 MB | 2586 ms | 12.9 ms |

**数据量 8 倍 → 耗时 7.6 倍**，标准的 O(N)。这就是下次做索引的理由
（稀疏索引 + 二分 → O(log N + 读一块)）。

- 用户初始状态：5 项全红，且给出的是**清单**不是崩溃。

**② 「迭代器只有一个 Begin，不完整吧？」** —— 他说得对，缺 `Seek`。

已补 **TODO 13：`SkipList::Seek(target)`** —— 跳到「第一个 key >= target」。

★ 关键：它必须长在 `SkipList` 上，**不能**长在 `Iterator` 上。
`Iterator` 手里只有 `node_`，够不到 `head_` 和 `level_`；嵌套类并不因为"在里面"
就能访问外层**对象**的成员。所以分工是：
**Iterator 持有位置，容器负责寻找位置**（STL 里 `map::lower_bound` 也是容器的成员）。

参考实现（已验证 7 种情况全过）：

```cpp
Iterator Seek(const std::string& target) const {
  const Node* p = head_;
  for (int i = level_ - 1; i >= 0; --i)
    while (p->next[i] != nullptr && p->next[i]->key < target) p = p->next[i];
  return Iterator(p->next[0]);
}
```

`<` 和 `<=` 差一个字符：写 `<=` 会漏掉「key 正好等于 target」那一条。

新增 `tests/test_iter.cpp` + `build.ps1 titer`：TODO 9 三项 + Seek 七项 + 墓碑遍历一项。
现状：TODO 9 全绿，Seek 四项红（还是 `return Begin()` 的占位）。

**③ 「head_ 是怎么更新的？我没看懂」** —— 这是今晚最好的问题。

答案是：**`head_` 从构造之后一次都没被改过。**

```cpp
head_ = NewNode("", "", RecordType::kPut, kMaxLevel);   // ← 全项目唯一一次写 head_
```

`Insert` 里三处出现 `head_`，全是**读**：

| 代码 | 在干什么 |
|---|---|
| `Node* p = head_;` | 取地址值，赋给局部变量 |
| `pre[i] = head_;` | 把地址值存进 `pre` 数组（升层时用） |
| `pre[i]->next[i] = n;` | `pre[i]` 恰好等于 `head_` 时，改的是**哨兵节点里的 next** |

三个东西必须分清，混在一起就永远看不懂：

```
head_            成员变量，在 SkipList 对象里      ← 只有构造时写它
head_ 指向的节点  堆上的哨兵，key 是空串           ← 永不移动、永不替换
head_->next[i]    哨兵内部的指针数组               ← Insert 改的一直是这个
```

所以「空表插入第一条」不是「head_ 指向新人」，而是「哨兵身后挂了个人」：
`head_->next[0] = n`。`head_` 自己的箭头纹丝不动。

**★ 哨兵的全部价值就在这一条**：第一个真节点和中间某个关键节点，插入代码
完全一样（都有前驱，都走 `pre[i]->next[i] = n`）。没有哨兵，每一层都要多写
一个 `if (pre[i] == nullptr) head_ = n;` 的分支。

**④ 他的 Insert 实现是对的**，顺带确认两点：
- `p` 在降层时**不回退**（不从 head_ 重新开始）—— 这是跳表查找的标准写法，
  低层的搜索范围是高层的子集
- 升层时 `pre[i] = head_` 必成立 —— 那些层现在是空的（`head_->next[lv] == nullptr`），
  新节点就是那一层的第一个，前驱只能是哨兵

# 两个格式问题已经有答案了（2026-10-18 定）

上次留的两个思考题，答案已经写进 `include/lsmkv/record.h` 的注释里：

**1. 写什么？（怎么区分存和删）**
