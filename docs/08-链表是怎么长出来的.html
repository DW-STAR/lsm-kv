链表是怎么长出来的

你睡前问的三件事：链表具体怎么构建 / RandomLevel() 的返回值插到哪 / 为什么要随机

2026-11-04 凌晨写 · 中间那块可以一步步点，从空表开始长

一句话答案，先给你个落脚点

跳表的链表不是一次性建好的，是每次 Insert 往里塞一个节点、连几根线长出来的。 RandomLevel() 只在 Insert 的第一行被调用一次，它的返回值就是这个新节点要连几根线——1 就只连 L0，3 就连 L0/L1/L2。随机是为了让「线」自己长成上疏下密的样子，不需要任何人去调整。

01RandomLevel() 的返回值去哪了

你写的 RandomLevel() 目前没有任何地方调用它——这就是你觉得「不知道它干了啥」的直接原因。它只在 Insert 里被调用，而且是第一件事：

bool SkipList::Insert(const std::string& key, const std::string& value, RecordType type) {
  // ── 第 1 步：先决定「这个新节点要连几根线」
  const int new_level = RandomLevel();          // ← 就是这里，返回值 = 层数

  // ── 第 2 步：Find，把每一层的「前驱」记下来
  std::vector<Node*> prevs(static_cast<size_t>(new_level), nullptr);
  Node* p = head_;
  for (int lv = level_ - 1; lv >= 0; --lv) {
    while (p->next[lv] != nullptr && p->next[lv]->key < key) p = p->next[lv];
    if (lv < new_level) prevs[lv] = p;          // 只记「新节点真的会用到的」那些层
  }

  // ── 第 3 步：如果新节点比现有最高层还高，先把多出来的层补起来
  if (new_level > level_) {
    for (int lv = level_; lv < new_level; ++lv) prevs[lv] = head_;   // ★ 关键一行
    level_ = new_level;
  }

  // ── 第 4 步：逐层挂线（顺序不能反）
  Node* n = NewNode(key, value, type, new_level);
  for (int lv = 0; lv < new_level; ++lv) {
    n->next[lv] = prevs[lv]->next[lv];
    prevs[lv]->next[lv] = n;
  }
  ++size_;
  return true;   // 严格来说 key 已存在时是「覆盖」不是「插入」，明天再处理
}
这段代码先看结构，别抄

明天你要自己写一遍。真正容易写错的是第 2 步的 `if (lv < new_level)` 和第 3 步的循环——为什么多出来的层前驱一定是 head_？因为那些层上现在一个节点都没有，能找到的「最后一个小于 key 的节点」只能是起点。
这正是 head_ 必须建 kMaxLevel 层的原因：它是唯一能在「新增一层」时充当起点的节点。

02从空表开始，一步一步长

下面这块是实的。每次点「插入下一个」，会往表里塞一个节点，显示它随机到了几层、连了哪几根线。注意看 level_ 怎么从 1 跳上去。

level_ = 1 size_ = 0
当前是空表：只有 head_ 一个节点，它的 next[0..11] 全是 nullptr，level_ = 1，size_ = 0。

五步里最需要看懂的是第 2 步

插入 b 时 RandomLevel() 返回了 3，而当时 level_ 还是 1。这时候发生了什么：

  1. new_level (3) > level_ (1) → 说明要长出新的一层；
  2. 新长出来的 L1、L2 上空无一人，所以这两个层的前驱只能是 head_，于是 prevs[1] = prevs[2] = head_；
  3. level_ = 3；
  4. 然后把 head_->next[1]、head_->next[2] 指向 b，b 的对应指针指向 nullptr。

如果 head_ 当初只建了 1 层，第 4 步就会读写 head_->next[1] 这个不存在的下标 → 越界。这就是「头节点必须 kMaxLevel 层」的全部理由，没有别的玄机。

另外注意一个容易看漏的细节：这一步里 prevs[0] = a，不是 head_。因为 L0 上已经有 a 了，「最后一个小于 b 的节点」就是 a。
所以准确的说法是：只有「新长出来的那几层」前驱才一定是 head_，已经在用的层仍然按 Find 的结果走。

反过来问一句

level_ 会降吗？不会。节点删光了它也不降。
因为它只是个「查找从哪层开始」的提示值，偏高无害——最多从一层空的开始，多降几次，浪费几十纳秒。
为省这点开销去维护「降层」逻辑（要扫全表看最高层还剩谁），完全不划算。「不维护也行的地方就别维护」是工程判断。

03为什么要随机

「层数随机」不是跳表的美学选择，是为了绕开一个具体的麻烦：如果层数不是随机的，就得有人负责在每次插入后调整索引，而调整索引很贵。

四种做法，逐个看代价：

做法长什么样代价
① 等距索引 每 4 个节点抽 1 个上浮到 L1，每 16 个抽 1 个到 L2…… 一插入就破功。中间塞一个，后面所有节点的「第几个」全变了，索引得跟着重排；删一个同理。最坏 O(n)。
要修好这个，就得引入「块满才分裂」——那已经是 B+ 树的路子了。
② 红黑树 / AVL 用旋转强制左右子树高度差不超过常数 旋转要改一片指针（父、子、叔、根），改到一半被别人读到就是错的 → 只能加锁。而且树的形状依赖全局约束，插入要一路回溯到根。
③ 按 key 哈希定层 level = f(hash(key))，同一个 key 永远同层 可行且可重现，但要额外保证哈希均匀；key 是任意字符串，还得先算哈希。比随机只多了一个「确定性」的好处，而跳表并不需要这个确定性。
④ 随机层数
（跳表选的）		 每层 1/2 概率，几何分布 插入只改 new_level 个前驱的 next 指针，没有全局约束，不需要任何重排。代价是「可能长得不好看」——但概率极低，见下。

随机的代价到底有多大

随机只影响性能，不影响正确性。哪怕所有节点都随机到 1 层，它依然是一条正确的有序链表，查询依然对——只是退化成 O(n)。

而「所有节点都 ≤ 1 层」的概率是 2⁻ⁿ：

节点数 n全部退化成单层的概率
10约 1 / 1000
100约 1 / 10³⁰
1000约 1 / 10³⁰¹（比硬盘位翻转的概率还低）

这就是「随机化数据结构」的核心交易：用「极低概率退化成 O(n)」，换掉「百分之百要做重平衡」的复杂度。红黑树是「保证最坏情况」，跳表是「几乎不可能出现最坏情况」——工程上后者更划算，因为你不需要写旋转，也不需要加锁。

为什么是 1/2，不是 1/4

课本（Pugh 1989 原始论文）用 1/2，你的代码里 (NextRandom() & 1) == 0 就是 1/2。但工业实现普遍用 1/4：

概率 p期望层数每个节点的平均指针数谁在用
1/22.002.00教材、本项目的第 1 版
1/41.331.33LevelDB（kBranching = 4）、Redis zset（ZSKIPLIST_P = 0.25）

换成 1/4 只要把那一行改成 (NextRandom() & 3) == 0，省下 1/3 的指针内存，代价是层数变浅一点点（查找多降几层，但每层走的步数也变少，几乎打平）。等你做完 MemTable 要压内存的时候，可以把这个当第一个调优点——那会是一个很好的 benchmark 对比数据（同一批数据，两种 p，内存和查找耗时各是多少）。

04「构建链表」这个说法要改一下

你问「怎么构建这个链表」，暗示的是「先有链表的形状，再往里填数据」。跳表不是这样，顺序是反的：

  • 不存在「先建好一条 3 层的索引链表」这一步；
  • 每次 Insert 只做两件事：① 找到该插的位置（每层各找一个前驱）② 把新节点的几根线接到这些前驱上；
  • 「多层索引」是你事后看整体结构的观感，不是任何一行代码直接建出来的。它是成百上千次「随机连 1~3 根线」累积出来的统计结果。
换个说法就通了

跳表的结构是涌现出来的，不是设计出来的。
代码里只有「单个节点怎么连线」这条局部规则，没有「整个索引长什么样」的全局代码。
你明天要写的 Insert，就是在定义这条局部规则。全局形态是它的副作用。

05明天写 Insert 时的三个坑

坑症状正确做法
两行赋值写反 新节点指向自己 → 查询死循环、CPU 打满 先 n->next[lv] = prevs[lv]->next[lv]，再 prevs[lv]->next[lv] = n
prevs 只开 level_ 大小 new_level > level_ 时写越界 → 堆损坏（可能很久以后才炸） 开 new_level 大小，不是 level_
升层时忘了补 prevs prevs[lv] 是 nullptr → 对空指针解引用，直接崩 多出来的层全填 head_，再改 level_

验证程序我会补进 demo_skip.cpp，会检查四件事：size_ 对不对、L0 全链严格升序、每个 next[lv] 指向的节点层数确实 > lv、插 1 万条后随机抽 1000 个 key 全查命中。第三条就是「不变量②」，它专抓「prevs 找错层」这类 bug。

06早上自测 3 题

1. 空表插入第一个节点，它随机到 5 层。这时候 head_->next[0..4] 分别是什么？

全部指向这个新节点。head_->next[5..11] 仍然是 nullptr，level_ 变成 5。
原因：prevs[0..4] 全是 head_（这五层上除 head 外没有别的节点），所以每一层都是「head → 新节点 → nullptr」。

2. 为什么 prevs 数组不能只开 level_ 那么大？举一个会炸的具体场景。

因为 RandomLevel() 可能返回比 level_ 大的值。例：level_ = 3，来了个 new_level = 5 的节点，你要写 prevs[3] 和 prevs[4]，但数组只有 3 个元素 → 越界写。
这类错误的恶劣之处：写坏的是堆上相邻的其它对象，可能几十行代码之后才崩，甚至只在 release 版崩。所以要开 new_level 大小。

3. 把所有节点的层数都改成「按 key 长度决定」（比如长度 1 → 1 层，长度 5 → 5 层），跳表还对吗？会出什么问题？

对的，依然正确。层数怎么定不影响正确性，只影响性能。
问题在于分布：插入的 key 长度一旦集中在某几个值上（比如全是 8 字节的 id），所有节点层数就一样了——要么全 1 层（退化成链表），要么全 8 层（每层都是全量，索引一点没稀疏，白占内存且查找没变快）。要保证「每层节点数大约减半」，就必须让层数与 key 无关、且独立随机。
